# Adaptive Factory M4 control plane with provisional M5 execution source

This nested Python package is a source-only, local control plane. It validates immutable M1/M2/M3/M0-bound intake, stores operational truth in an isolated PostgreSQL `factory` schema, schedules work with database leases and monotonic fences, enforces 20 global readers / 10 readers per repository / one writer, bounds retries and budgets, retains hash-chained audit, and performs restart-safe reconciliation.

The provisional M5 source adds four closed execution schemas, a closed 20-operation local OpenAPI contract, provider-neutral packets/protocol, fixture-only adapters, proposal persistence, trusted artifact-attestation capabilities, factual workspace results, bounded restart recovery, six fixed metric families and four inert source systemd units. It does not execute live providers, shell or repository commands; access Git/GitHub, Trust CI state or credentials; install or activate systemd; deploy; publish; or perform an external/production write. `ready_for_human` remains the M4 positive terminal state; recovery emits only one control-plane `orphaned` stage/event, with no terminal proposal and no WorkspaceResult fabrication.

## Execution contracts and M6 boundary

The authoritative wire inventory is [`task-packet.v1.json`](contracts/schemas/task-packet.v1.json), [`execution-invocation.v1.json`](contracts/schemas/execution-invocation.v1.json), [`execution-event.v1.json`](contracts/schemas/execution-event.v1.json), [`workspace-result.v1.json`](contracts/schemas/workspace-result.v1.json) and [`factory-control.v1.json`](contracts/openapi/factory-control.v1.json). All nested JSON objects are closed; the OpenAPI file inventories 20 operation IDs, required mutation headers and bodies, explicit response variants and correlation headers.

M4 remains authoritative for task state, run, lease, fence, allocation, deadline and budget. M5 binds those facts into immutable `TaskPacketV1`, `RunManifestV1`, proposal and `WorkspaceResultV1` digests. A later M6 consumer may read only the exact verified packet/manifest/snapshot/result bundle after restack; provider facts are not authority, fake brokers are not authority, and no M5 or M6 component can create semantic acceptance or self-approval.

## Local API and CLI

The supported composition command is `adaptive-factory-server`. It builds the store, service, authenticator and ASGI application, then pre-binds only an operator-owned Unix socket (default `/run/adaptive-factory/control.sock`) at mode `0660`; there is no TCP option. The socket parent must be owned by the process user and not group/world writable. Actor configuration and every referenced token file require an absolute, owner-pinned, no-follow descriptor walk and a mode-`0600` leaf; see `actors.example.json`. The service login must be a `NOINHERIT` member of `factory_runtime`: every store connection executes `SET ROLE factory_runtime`, while migrations use a separate owner connection.

Before intake, an independently verified M0 observation (or separately approved bootstrap exception) must be provisioned into the matching immutable `factory.m0_*` table by the operator boundary. Caller JSON is only a lookup key and cannot originate authority. Budget reservation and usage observation are authenticated worker endpoints; completion is rejected until accounting is present, settled and unblocked.

All mutations require `Idempotency-Key` and `X-Correlation-ID`. Bodies are at most 1 MiB; list/reconcile pages are at most 100. Credentials, raw bodies/prompts, reasoning, native streams, unrestricted output and task IDs as metric labels are prohibited.

Configuration names are documented in `.env.example`; it contains placeholders only. For a newly created, explicitly disposable local database, load those names into the shell, start `docker compose up -d postgres`, and run `adaptive-factory-admin bootstrap-local`. That command applies checksum migrations with `FACTORY_MIGRATOR_DATABASE_URL`, creates or validates distinct bounded runtime and artifact-attestor logins, proves their exclusive `factory_runtime` and `factory_artifact_attestor` effective roles, and rejects dual or excess membership. The attestor DSN supplies only protected evidence recording: it is never treated as a workspace observer, so artifact proposals remain unavailable unless a separate trusted observer is explicitly injected. `adaptive-factory-admin migrate` is the migration-only interface. Do not point either command at a shared, external, Trust CI or production database. Source delivery does not run either command or activate a service.

## Readiness, observation and recovery

`/health/ready` checks the effective `factory_runtime` role and exact schema version. Authenticated `/metrics` returns exactly six fixed low-cardinality JSON families: the three M4 families plus execution claim/stage, protocol/proposal and orphan/cleanup outcomes. Every final application response with status 401 or 403 is counted once in a concurrency-safe process-local total; all durable values come from one fixed-row PostgreSQL snapshot with bounded timeouts. Proposal metrics increment only on unique insert, orphan metrics only on unique terminalization and workspace cleanup only on an actual first fake release. Metrics never label task/source/actor IDs or emit bodies, credentials, tokens, reasons or reasoning.

For a separately approved local M4 rollout: preserve the distinct owner and runtime DSNs, start killed, verify a logical backup by restoring it into a distinct comparison database, run the admin bootstrap/migration interface through exact schema `013`, then start `adaptive-factory-server` only with the runtime DSN. Schedule the `012` atomic metrics cutover and `013` retry-limit backfill only after confirming their bounded lock/scan work fits the local migration window. Check readiness/metrics including capacity/allocation, retry-limit and claimable/positive-endpoint accounting agreement; run synthetic submit/claim/reserve/observe/release/restart/reconcile twice; then clear kill. On any M4 invariant failure, enable global kill, stop the socket process, preserve state/audit/logs, and forward-fix with migration `014+`.

No M5 rollout is authorized from this tree. The four files under `systemd/` are source topology only: they have `ExecCondition=/usr/bin/false`, no `[Install]` section and no runnable provider command. The installer copies source/contracts/fixtures/tests/units only; it never enables or starts a unit, runs migration `014`, creates a database/login/credential/runtime directory or contacts an external system. A later accepted M5 rollout requires dependency-ordered restack, fresh exact-tree evidence, independent review, external Trust CI and the dedicated rootless-host and trusted-Git-snapshot gates. Once execution migration `014` is durable, any execution-plane schema repair must be forward-only as migration `015+`.
