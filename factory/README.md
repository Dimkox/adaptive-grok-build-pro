# Adaptive Factory M4 control plane with provisional M5 execution

This nested Python package is a source-only, local control plane. It validates immutable M1/M2/M3/M0-bound intake, stores operational truth in an isolated PostgreSQL `factory` schema, schedules work with database leases and monotonic fences, enforces 20 global readers / 10 readers per repository / one writer, bounds retries and budgets, retains hash-chained audit, and performs restart-safe reconciliation.

It does not make a live provider call, run a repository command, access GitHub/Trust CI credentials, install systemd, deploy, publish, or perform an external/production write. `ready_for_human` remains M4's positive terminal state. Provisional M5 source adds provider-neutral contracts/protocol, fixture-only adapters, trusted proposal/workspace interfaces, an execution HTTP surface, PostgreSQL execution persistence through migration `017`, atomic terminal finalization, and bounded at-least-once workspace cleanup. It creates no production execution authority.

## Local disposable verification

Use a freshly created disposable PostgreSQL 17+ database only. Integrated M5 recovery deliberately requires PostgreSQL 17 `transaction_timeout`; PostgreSQL 15/16 fail before migration `017` mutates schema state. Never reuse a Trust CI/shared/production URL or inspect an existing `.env`.

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
FACTORY_TEST_DATABASE_URL='postgresql://factory_test:replace@127.0.0.1:5432/factory_test' \
  .venv/bin/python -m unittest tests.test_postgres_integration -v
```

The migration runner uses a factory-only advisory lock and immutable packaged checksums. M4 ends at `013`. M5 `014` adds execution packets/manifests/events/proposals, `015` expands canonical proposal/attestation/result persistence and trusted finalization, `016` drops only superseded provisional constraints in the same migrator transaction, and `017` adds fail-closed PostgreSQL-17 recovery jobs/claims/outcomes plus fixed atomic metrics. Migrations do not fabricate proposals, results or attestations. After durable intake, rollback is global kill + preserved audit + backup restore into a separate comparison database or a reviewed forward migration `018+`; never down-migrate or delete evidence.

## Local API and CLI

The supported composition command is `adaptive-factory-server`. It builds the store, service, authenticator and ASGI application, then pre-binds only an operator-owned Unix socket (default `/run/adaptive-factory/control.sock`) at mode `0660`; there is no TCP option. The socket parent must be owned by the process user and not group/world writable. Actor configuration and every referenced token file require an absolute, owner-pinned, no-follow descriptor walk and a mode-`0600` leaf; see `actors.example.json`. The service login must be a `NOINHERIT` member of `factory_runtime`: every store connection executes `SET ROLE factory_runtime`, while migrations use a separate owner connection.

Before intake, an independently verified M0 observation (or separately approved bootstrap exception) must be provisioned into the matching immutable `factory.m0_*` table by the operator boundary. Caller JSON is only a lookup key and cannot originate authority. Budget reservation and usage observation are authenticated worker endpoints; completion is rejected until accounting is present, settled and unblocked.

All mutations require `Idempotency-Key` and `X-Correlation-ID`. Bodies are at most 1 MiB; list pages are at most 100 and execution recovery uses a two-lane limit of 2..100. `/v1/execution/*` preserves the enrolled v1 response contract; additive `/v2/execution/*` exposes the strict route-specific terminal completion result. Both terminal routes run the same server-owned proposal → trusted snapshot → finalization saga; clients never supply a snapshot. Credentials, raw bodies/prompts, reasoning, native streams, unrestricted output and task IDs as metric labels are prohibited.

M4 configuration names are documented in `.env.example`; it contains placeholders only. The provisional M5 execution flag and artifact-attestor login/password/DSN names are not yet present in that template and remain an explicit successor-06 configuration-parity task, so the template must not be treated as sufficient for enabled M5 composition. For a newly created, explicitly disposable local database, load the documented M4 names into the shell, start `docker compose up -d postgres`, and run `adaptive-factory-admin bootstrap-local`. That command applies checksum migrations with `FACTORY_MIGRATOR_DATABASE_URL`, creates or validates the bounded `FACTORY_RUNTIME_LOGIN`, grants only `factory_runtime`, and proves `FACTORY_DATABASE_URL` reaches readiness under the effective role; `adaptive-factory-admin migrate` is the migration-only interface. Do not point either command at a shared, external, Trust CI or production database. Source delivery does not run either command or activate a service.

## Readiness, observation and recovery

`/health/ready` checks the effective `factory_runtime` role and exact schema version `17`. Recovery capabilities require bounded statement, lock and transaction timeouts; the coordinator has a 30-second monotonic invocation budget and advances a fresh-page cursor only through authoritatively processed rows. Fresh discovery and due cleanup retries share a work-conserving bounded page without starving either lane. Workspace release is exact-handle, deterministic and idempotent, but deliberately at-least-once after claim TTL/crash: a later fence may call release again, `already_absent` is success, and stale completion is rejected. Cancel and supersede project cleanup transactionally; recovery never invents a terminal proposal or workspace result. Authenticated metrics come from one fixed-row stable snapshot and expose only low-cardinality families. The self-contained probe now proves these facts across two actual PostgreSQL restarts with distinct reconstructed runtime/attestor sessions, durable failure→fence-2 cleanup, unchanged evidence and rejected stale holders. This is local source evidence, not an M5 exit or operational-isolation claim.

No M5 rollout is currently approved. A future local rollout must preserve distinct owner/runtime/attestor DSNs, start killed, restore a verified backup into a separate comparison database, apply through exact schema `17`, prove role/readiness/metrics and the two-restart recovery drill, and then separately prove the trusted rootless broker plus live credential/egress isolation. Those operational isolation gates are currently blocked. On any invariant failure, enable global kill, stop execution claims and the socket process, preserve state/audit/logs, and forward-fix with migration `018+`.
