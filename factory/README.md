## Local disposable verification

Use a freshly created disposable PostgreSQL 15+ database only. Never reuse a Trust CI/shared/production URL or inspect an existing `.env`.

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
FACTORY_TEST_DATABASE_URL='postgresql://factory_test:replace@127.0.0.1:5432/factory_test' \
  .venv/bin/python -m unittest tests.test_postgres_integration -v
```

The migration runner uses a factory-only advisory lock and immutable packaged checksums. Migration `005` adds trusted M0, command replay and accounting controls; migration `006` removes runtime policy/identity updates; migration `007` makes 20/10/1 capacity canonical and exposes only capability-shaped allocation/release functions; migration `008` removes runtime authority to hide or restore allocations; migration `009` binds M0 subjects and audit-v2 evidence and adds task-history indexes; migration `010` serializes authority revocation, quarantines legacy unresolved accounting and separates mandatory cleanup facts from the ordinary event budget; migration `011` completes schema-008 quarantine for blocked-zero retry and unsafe positive endpoints, using evidence-preserving `superseded/accounting_blocked` for an unsafe older generation when a newer generation exists. Migration `011` is unreleased and was corrected before PR delivery; any disposable database holding its earlier checksum must be discarded and recreated. Migration `012` replaces runtime-writable generic metrics with an owner-maintained, transactionally updated singleton snapshot, preserves the old rows only as locked untrusted evidence, and grants runtime only fixed snapshot and no-argument saturating fence capabilities. Its atomic cutover takes write-blocking source-table locks and intentionally resets the trusted fence counter to zero because pre-`012` runtime could forge that value; a timeout or lock failure rolls the entire migration back and requires an operator-reviewed retry window. After durable intake, rollback is global kill + preserved audit + backup restore into a separate comparison database or forward migration `013+`; never down-migrate or delete evidence.

## Local API and CLI

The supported composition command is `adaptive-factory-server`. It builds the store, service, authenticator and ASGI application, then pre-binds only an operator-owned Unix socket (default `/run/adaptive-factory/control.sock`) at mode `0660`; there is no TCP option. The socket parent must be owned by the process user and not group/world writable. Actor configuration and every referenced token file require an absolute, owner-pinned, no-follow descriptor walk and a mode-`0600` leaf; see `actors.example.json`. The service login must be a `NOINHERIT` member of `factory_runtime`: every store connection executes `SET ROLE factory_runtime`, while migrations use a separate owner connection.

Before intake, an independently verified M0 observation (or separately approved bootstrap exception) must be provisioned into the matching immutable `factory.m0_*` table by the operator boundary. Caller JSON is only a lookup key and cannot originate authority. Budget reservation and usage observation are authenticated worker endpoints; completion is rejected until accounting is present, settled and unblocked.

All mutations require `Idempotency-Key` and `X-Correlation-ID`. Bodies are at most 1 MiB; list/reconcile pages are at most 100. Credentials, raw bodies/prompts, reasoning, native streams, unrestricted output and task IDs as metric labels are prohibited.

Configuration names are documented in `.env.example`; it contains placeholders only. For a newly created, explicitly disposable local database, load those names into the shell, start `docker compose up -d postgres`, and run `adaptive-factory-admin bootstrap-local`. That command applies checksum migrations with `FACTORY_MIGRATOR_DATABASE_URL`, creates or validates the bounded `FACTORY_RUNTIME_LOGIN`, grants only `factory_runtime`, and proves `FACTORY_DATABASE_URL` reaches readiness under the effective role; `adaptive-factory-admin migrate` is the migration-only interface. Do not point either command at a shared, external, Trust CI or production database. Source delivery does not run either command or activate a service.

## Readiness, observation and recovery

`/health/ready` checks the effective `factory_runtime` role and exact schema version. Authenticated `/metrics` returns only three fixed low-cardinality JSON families covering intake, queue/retry/dead states, transition events, live/reclaimed leases, fence rejections, capacity, reserved/observed budget, accounting blocks, active kills and reconciliation candidates/repairs. Every final application response with status 401 or 403 is counted once in a concurrency-safe process-local total, including authentication, scope, actor-kind, repository and trusted-authority rejection; that value starts at zero whenever the socket server restarts and has no reset endpoint. All other values come from one fixed-row PostgreSQL snapshot maintained in the same transactions as authoritative writes and read with a 5-second statement timeout and 500-millisecond lock timeout. Fence rejection accounting is a bounded best-effort observation after the authoritative stale-fence decision: connection/lock/statement failure can omit that increment, but can never replace or materially delay the stable `409 stale_fence` response. Metrics never label task/source/actor IDs or emit bodies, credentials, tokens, reasons or reasoning. `python3 scripts/grok_verify.py --mode pr` creates a disposable PostgreSQL 17 container, executes API/database/effective-role tests, performs an actual database restart, reconciles twice, and removes that exact container.

For a separately approved local rollout: preserve the distinct owner and runtime DSNs, start killed, verify a logical backup by restoring it into a distinct comparison database, run the admin bootstrap/migration interface through exact schema `012`, then start `adaptive-factory-server` only with the runtime DSN. Schedule the `012` atomic cutover only after confirming its bounded source-table lock/scan can finish inside the local migration window. Check readiness/metrics including capacity/allocation and claimable/positive-endpoint accounting agreement; run synthetic submit/claim/reserve/observe/release/restart/reconcile twice; then clear kill. On any invariant failure, enable global kill, stop the socket process, preserve state/audit/logs, and forward-fix with migration `013+`.
