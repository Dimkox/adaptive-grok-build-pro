## Problem

`HTTP_PROFILES` bound the omni model to the mainland host, and `selected_profile`/provider enums only ever offered omni there, while the provisioned key on this host is an international-account key and DashScope keys are region-bound. The five-media capability was therefore unreachable by configuration — issue #86. The env composition gate `compose_env_landing` additionally refused *both* omni names, so even the mainland omni could not be composed from the environment. Separately, the operator probe collapsed every failure into `qwen_probe_failed`, so an authentication rejection looked identical to a timeout or a malformed stream — the one half of issue #87 that #91 did not close.

## Live proof, not documentation

Before changing anything, the claim was tested against the provider with the request shape the product itself builds (`_request_body` / `_user_content`), streaming, `modalities: ["text"]`, `stream_options` usage:

```text
intl/image   : HTTP 200 model=qwen3.5-omni-plus-2026-03-15 finish=stop done=True
               usage prompt_tokens_details={image_tokens: 66, text_tokens: 41}
               answer='The image contains a red square on a blue background.'
intl/audio   : HTTP 200 model=qwen3.5-omni-plus-2026-03-15 finish=stop done=True
               usage prompt_tokens_details={audio_tokens: 2, text_tokens: 37}
               answer='A single, steady, high-pitched electronic tone is heard.'
mainland(img): HTTP 401 invalid_api_key   <- reproduces #86 with the same key today
```

The inputs were generated by this change (`evidence/live-omni-probe.md`): a 64×64 PNG with a red square on blue and a 0.4 s 880 Hz mono WAV. Both answers describe what was actually sent, and the token accounting proves the media reached the model rather than being ignored. The credential was read from the process environment by the script and never entered a transcript, a diff or this repository.

## Changes

- `qwen-omni-intl` profile: international host, same pinned model, streaming, five media classes; accepted by the host-config validator, the settings enum, `compose_env_landing` (which now admits both omni names) and the probe choices.
- Probe failure output becomes `{state, reason, category, http_status}` with `category` restricted to the seven allowlisted classes; the closed-output property is asserted, not asserted away.
- Untouched on purpose: `PROVIDER_ORDER` (failover chain) and the mainland `qwen-omni` binding, so no existing installation changes live routing.

## Not established

This is not acceptance of multimodal landing: no service was enabled, started or installed, no task was published through omni, and pilot acceptance, M8 cohort/activation and M9 qualification remain unproven. What is established is that the profile can be selected and that the endpoint answers the media correctly with the provisioned key.
