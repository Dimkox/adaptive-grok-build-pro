# Design packet: #97 / #96 review evidence lifecycle

This is a scoped successor design, not implementation or approval. Source is current `main` plus fetched open PR [#134](https://github.com/Dimkox/adaptive-grok-build-pro/pull/134), `fix/agent-evidence-claims` at `25d7a2b958a1435bf794112e253bc3a6ab64dd73`, fetched during this route. Issue #117 owns that PR. The reported #97 fabricated verdict occurred while reviewer agents were still running; #96's completed reviewer returned a verdict without writing its required file, then its resume crashed with `DOMException`.

## Overlap decision

**Reuse PR #134; do not create a parallel validator.** On current `main`, `scripts/grok_review.py` only tests `is_file()` and `.grok-stack/adaptive_grok/receipts.py::write_receipt` stores the caller's path/status without reading the report. PR #134 adds `.grok-stack/adaptive_grok/review_evidence.py`, `docs/review-report-v1.md`, changes both call sites, and adds `tests/test_review_evidence.py`. Its v1 validator requires a bounded UTF-8 JSON report with nonempty claims, `review_kind` and `status` matching the receipt, confined regular files and source spans, and a report-byte SHA-256 bound into the receipt. `validate_evidence` revalidates the report and digest. Its tests include missing/escaping/oversized reports, status mismatch, unsupported claim shape, modified/deleted report, and a pass receipt without structured report. This directly closes the durable-placeholder variant of #97 and the missing-file variant of #96 once delivered.

PR #134 is open, not current `main`; its reported external check success is exact-head evidence for that PR only and not delivery of this research route. It does not authenticate author identity, prove a tool command ran, observe whether a subagent reached terminal completion, or police an assistant's user-facing prose. `docs/review-report-v1.md` explicitly labels execution claims `self_reported_unverified`. #97's invented findings cannot be prevented merely by parsing a syntactically valid JSON claim if the agent fabricates its content.

## Existing report forms and compatibility

Legacy reports are plain Markdown with no stable schema. Current examples start with `VERDICT: pass` (`.../issue-155.../evidence/code-review.md`), `PASS` (`.../issue-146.../evidence/review-security.md`), or a title followed by `**PASS.**` (`.../quality-contour.../evidence/code-review.md`). They mix findings, unverified notes and evidence. A regex for a PASS word would accept fabricated prose and accidentally reject legitimate old layouts. PR #134 explicitly makes legacy prose ineligible for **new** passing receipts; it does not rewrite archived reports. On an active route created before #134 with only Markdown reports, a new receipt after that PR will require a freshly authored v1 JSON report. Do not silently wrap old prose and label it validated execution.

## Bounded residual outcome

After #134 lands, add only a workflow completion rule and, if the owner wants machine enforcement, a narrow completion guard: route-selected reviewer writes the report first, then sends a short summary containing its exact path; coordinator reads and validates that path before narrating verdict or recording a receipt. If the agent ends or crashes without the file, the state is `no report`, regardless of its chat verdict. A `failed` agent can be retried only as a new bounded review; do not resume a completed agent solely to create a missing artifact. The parent may read the report it explicitly requested; no transcript recovery is needed to claim a review. If structured report validation itself is added as a gate, use PR #134's validator and refuse stale/digest-mismatched artifacts.

Acceptance checks: (1) an unfinished or failed reviewer with no file cannot produce a pass receipt or a completed review claim; (2) a missing, empty, placeholder, wrong-kind/status, or changed v1 report is rejected at receipt authoring or validation; (3) a valid v1 report remains local advisory evidence, clearly identifying self-reported execution; (4) archived Markdown stays archived, and a new pass receipt requires v1 JSON; (5) failure text distinguishes `agent failed`, `report missing`, `report invalid`, and `receipt stale`. Existing PR #134 covers (2) and much of (3)-(4); route instructions/coordinator behavior cover (1) and (5). Tests for a coordinator completion guard should use synthetic agent statuses and temp report files, not actual provider crashes.

Implementation boundaries: modify the route-selected reviewer prompt/coordination contract only after PR #134 is integrated or restacked, and avoid schema duplication. If a terminal agent status is not available to the repository-side coordinator, make the receipt/report artifact rule enforceable and document status as externally observed only. Do not turn local receipts into merge authority; App-owned Trust CI and signed approvals remain separate. Rollback of the residual rule is a documentation/coordinator revert; rollback of PR #134 is its own review because removing digest checks permits old false-green receipts again.

Named scope decision for owner: accept PR #134's v1-only new-pass policy, with archived prose retained as historical evidence, then decide whether a separate coordinator implementation is warranted. The report path/digest guard itself is already scoped and implemented in #134; #96's `DOMException` resume failure belongs to the agent host.
