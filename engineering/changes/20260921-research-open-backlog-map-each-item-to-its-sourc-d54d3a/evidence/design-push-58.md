# Design packet: #58 exact-source branch push

This is a security-sensitive candidate for a separate route and named scope decision. No push, grant, remote mutation, or test execution occurred in this research. Asset: a PR branch ref and its reviewed exact commit. Actors: user delegating one operation, local agent/helper, local Git worktrees, Git remote. Trust boundary: the repository hook and local grants are advisory workflow controls; the remote enforces a normal push's fast-forward rule, and App-owned Trust CI remains the merge authority for protected `main`.

## Current gap and existing protections

`.grok/hooks/_lib.py::root_context` resolves session, tool workdir, shell `cd`, and `git -C` roots and rejects cross-root/ambiguous sensitive commands. `.grok-stack/adaptive_grok/_policy_legacy.py::evaluate_pre_tool` classifies `git push` as `git-push-branch`/tag and requires a valid production grant. `.grok-stack/adaptive_grok/state.py::add_approval` binds route, change, repository, `git_head`, tree fingerprint and TTL. However, production grants do **not** require resources (`state.py:217-219` requires them only for protected/external scopes), and `has_valid_approval(... action=...)` is called without the destination ref. The parser does not establish the pushed `<src>` as that grant's `git_head`. Thus a granted ordinary `git push origin HEAD:refs/heads/x` can send the wrong worktree's HEAD. The current `DESTRUCTIVE_COMMANDS` already rejects `git push ... --force-with-lease` and `--force`; keep that denial. The project hook explicitly fails open on import/policy errors (`.grok/hooks/pre_tool_use.py`), so it cannot be described as a server-side guarantee.

## Small coherent correction

Provide one supported branch-push operation that accepts an **exact 40-hex source commit** and **one full destination `refs/heads/<name>`**, plus an explicit repository/worktree path. Require a production `git-push-branch` grant whose resource exactly equals that destination, with no wildcard. Bind the supplied source to the grant's current `git_head` and recheck tree fingerprint just before executing. Resolve the repository and source via `git -C <path> rev-parse`; reject detached ambiguity, `HEAD`, `.`, branch names, multiple refspecs, shell composition, `--force*`, deletion refspecs, tags, alternate remotes, and any mismatched path/ref/source. Show the resolved source SHA, destination, and remote tip in a dry-run/plan output before an operation is delegated.

At execution, independently read `refs/heads/<name>` from the configured remote (`git ls-remote --heads`), reject unexpected missing branch unless branch creation is explicitly in scope, and check `git merge-base --is-ancestor <remote-tip> <source>` locally. Then invoke a **single** normal `git -C <path> push <remote> <source-sha>:<full-ref>` with no `--force`, no shell, no `||` fallback. The remote's atomic fast-forward check handles races after `ls-remote`: if the tip advanced incompatibly, push fails and no automatic retry occurs. Observe the remote ref after success and record source SHA and resulting ref as local evidence. The preflight remote-tip read is diagnostic and may itself be stale; do not treat it as a lease or attestation. An exact delegated grant is still required to execute; this design grants no authority by itself.

Implementation paths: a dedicated helper under `scripts/` and `.grok-stack/adaptive_grok/` for strict argv/subprocess execution; `state.py`/`grok_approve.py` resource requirement for branch-push grants; `policy.py`/`_policy_legacy.py` to reject raw ambiguous or unscoped push shapes when the hook runs; `tests/test_hooks.py` and focused helper tests. Update `AGENTS.md` and the release/push runbook with one-command/one-effect guidance. Decide separately whether tag pushes use the same exact-resource rule; do not silently change release behavior as part of #58. Avoid touching external Trust CI policy, branch protection, host credentials, or GitHub App material.

Acceptance tests use two synthetic linked worktrees and a local bare remote. A grant issued for worktree A/ref A cannot push worktree B's HEAD or ref B; a `cd`/`pushd`/pipe/`||` composition is refused; `HEAD` and `--force-with-lease` are refused; one exact source/ref fast-forward push succeeds; a remote that advances or diverges causes a refused normal push with no fallback; a changed tree/HEAD expires the grant. Tests must inspect the remote ref before and after a rejection to prove no mutation. The existing tests that allow a granted bare `git push origin feature` need deliberate updates in the same change. A hook fail-open case should demonstrate that the helper itself still refuses an invalid invocation, without claiming it can prevent arbitrary raw `git` outside the helper.

Rollout: introduce the helper and explicit branch-resource grant as an additive path; migrate the documented delegated branch-push flow, then reject legacy raw push command shapes locally. Recovery from a rejected or failed push is read-only inspection and a new exact plan/grant; never automatic force or retry. A source branch accidentally moved by an operator outside this path still requires separate human-controlled remote recovery. If compatibility with existing production grants is needed, the owner must decide it explicitly; default is fail closed for future branch pushes.

Named scope decision for owner: authorize **only** the design/implementation of exact-source branch pushes through the local helper and per-ref delegated grants. Any actual push remains a separate named operation with exact repository/ref/source and current grant. This packet does not request or supply that operational delegation.
