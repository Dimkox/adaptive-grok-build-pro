# Composition-keyword semantics + compatibility-checker convention (docs research)

Research only. "Spec" = normative text I opened; "tool" = a checker's documented policy; "unverified" = search-narrated only.
L(S) = set of instances valid against S. Bidirectional gate: `consumer accepts old` ⟺ L(old) ⊆ L(new); `producer accepted by old` ⟺ L(new) ⊆ L(old). Both hold ⟺ L(old)=L(new), i.e. a strict bidirectional gate is a **language-equality** gate.
Spec anchors: IETF draft text §10.2.1.1–.4 gives allOf "validates … against all schemas", anyOf "at least one schema", oneOf "exactly one schema", not "valid … if it fails to validate" (https://www.ietf.org/archive/id/draft-bhutton-json-schema-01.txt; same text on the published page https://json-schema.org/draft/2020-12/json-schema-core). Order-independence, verbatim §10.2 of that core page: "Subschemas of these keywords evaluate the instance completely independently such that the results of one such subschema MUST NOT impact the results of sibling subschemas. Therefore subschemas may be applied in any order." Inclusive-vs-exclusive and "Multiple of _both_ 5 and 3 is rejected": https://json-schema.org/understanding-json-schema/reference/combining.

## 1. Change classes

| change | L changes? | direction | bidirectional verdict |
|---|---|---|---|
| reorder branches (anyOf/oneOf/allOf) | No | equal | not a break; reporting it is over-strict but sound |
| add branch, anyOf | Yes | superset (widen) | fails `producer accepted by old` only |
| add branch, allOf | Yes | subset (narrow) | fails `consumer accepts old` only |
| add branch, oneOf | Yes | **incomparable** | fails BOTH (new branch also steals exclusivity) |
| remove branch, anyOf | Yes, unless the branch was subsumed → equal | subset | fails `consumer accepts old` only |
| remove branch, allOf | Yes, unless redundant → equal | superset | fails `producer accepted by old` only |
| nested constraint inside a branch | depends | superset/subset/**incomparable** | undecidable syntactically |
| anyOf→oneOf, same branches | Yes | subset (strict unless disjoint) | fails `consumer accepts old` |
| oneOf→anyOf, same branches | Yes | superset (equal iff disjoint) | fails `producer accepted by old` |

## 2. Blanket fail-closed on any structural change to a composition value

Sound for "never certify a real break" (it can only over-report), but it is not a compatibility oracle: it rejects the change class every mature checker grades non-breaking (additive widening on the accepting side), and it cannot be re-narrowed per direction without a re-audit.
* oasdiff (https://www.oasdiff.com/docs/breaking-changes, Schema area, read directly): `request-body-any-of-added`=**Info**, `request-body-any-of-removed`=**Breaking**, `request-body-one-of-added`=Info, `request-body-one-of-removed`=Breaking; mirrored for responses (`response-body-any-of-added`=Breaking, `-removed`=Info; oneOf added=Breaking, removed=Info); allOf inverted (`request-body-all-of-added`=Breaking, `-removed`=Info, `response-body-all-of-removed`=Breaking, `-added`=Info). Stated principle: "A change is breaking if a consumer that followed the old contract can stop working under the new one", with narrowing a request and widening a response the breaking directions. **No reordering rule exists** in that catalogue. Caveat: a search rendering of oasdiff's *Parameters* area showed opposite severities for the same IDs — trust only the Schema-area table I read.
* oasdiff documents the mirror error too: an allOf subschema "identical to a previously existing subschema" reported as breaking "isn't a breaking change", mitigated by `--flatten-allof`, which loses file/line/column (https://raw.githubusercontent.com/oasdiff/oasdiff/main/docs/ALLOF.md). Its posture for undecidable constructs is severity demotion (ERR/WARN/INFO, "cannot be confirmed programmatically as breaking"), plus an explicit "annotation-only (no wire-contract effect)" INFO rule — i.e. tools narrow severity rather than going fully fail-closed.
* Confluent (https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html): BACKWARD = "consumers using the new schema can read data produced with the last schema"; FORWARD = "data produced with a new schema can be read by consumers using the last schema"; FULL = both — exactly the two directions above. Its Avro/Protobuf table grades "Add union/oneof variant" and "Remove union/oneof variant" as separate rows (cell marks unreliable through fetch summarisation, and secondary commentary says adding a oneof field is forward-incompatible → **conflict, low confidence**).
* Confluent JSON Schema (https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/serdes-json.html, verbatim): "Unions are implemented with the `oneOf` keyword in JSON Schema." and "If the reader's and writer's schemas are both unions, then the writer's schema must be a subset of the reader's schema." — a **set-subset** test, not a positional diff.
* Yokota (author of that logic) defines the directions as document-set inclusions: "Backward compatibility – all documents that conform to the previous version of the schema are also valid according to the new version" (https://yokota.blog/2021-03-29/understanding-json-schema-compatibility/).

## 3. Empty cases (bounded-validator decision)

* `allOf: []`, `anyOf: []`, `oneOf: []` are **non-conforming**: "This keyword's value MUST be a non-empty array" (draft-bhutton §10.2.1.1–.3; the same MUST appears on the published core page), and the machine-readable meta-schema enforces it — `"$defs": {"schemaArray": {"type": "array", "minItems": 1, "items": {"$dynamicRef": "#meta"}}}` with allOf/anyOf/oneOf each `$ref`-ing it (https://json-schema.org/draft/2020-12/meta/applicator). ⇒ **reject** `anyOf: []` as an invalid schema.
* If evaluated anyway: "at least one of ∅" = match-**nothing**; "exactly one of ∅" = match-**nothing**; "all of ∅" = vacuous match-anything. `anyOf: []` is never match-anything.
* `{}` = "An empty schema is a JSON Schema with no properties, or only unknown properties"; `true` "Always passes validation, as if the empty schema {}"; `false` always fails (core §4.3.1–4.3.2). `not: {}` means the instance must fail something every instance passes ⇒ **match-nothing** (unsatisfiable), not "anything goes".

## 4. `not` and `if`/`then`/`else`: is an anyOf-only subset coherent?

Yes, as a *declared* restriction — and only if unadmitted keywords are **rejected**, not silently ignored. Spec: the applicators "can only cause assertion failures by using the false boolean schema, or by inverting the result of the true boolean schema" (Appendix A, https://json-schema.org/draft/2020-12/json-schema-validation) — `not` is exactly that inversion, so it makes L complement-shaped (non-monotone) and a positive-union comparator cannot bound it; `not` is a core applicator keyword (meta/applicator above), not optional sugar. Conditionals (https://json-schema.org/understanding-json-schema/reference/conditionals): "If `if` is valid, `then` must also be valid (and `else` is ignored.) If `if` is invalid, `else` must also be valid (and `then` is ignored)."; "If `then` or `else` is not defined, `if` behaves as if they have a value of `true`."; "If `then` and/or `else` appear in a schema without `if`, `then` and `else` are ignored" — so a bare `else` is inert and refusing it loses no asserted language that `if` alone carries. Tool precedent for fail-closed on conditionals: oasdiff's design issue states "Complex to analyze breaking-ness — treat any change as a potential breaking change" (https://github.com/oasdiff/oasdiff/issues/793, unverified).
OpenAPI 3.1 (https://spec.openapis.org/oas/v3.1.0, verbatim): "Data types in the OAS are based on the types supported by the JSON Schema Specification Draft 2020-12 … Models are defined using the Schema Object, which is a superset of JSON Schema Specification Draft 2020-12." So 3.1 *adds* keywords and changes `$ref`/base-URI resolution rather than restricting the keyword set; 3.0-era tooling diverged in practice (`type: ["string","null"]` rejected by validators that wanted `nullable` — Speccy error quoted in https://apisyouwonthate.com/blog/openapi-json-schema-divergence/).

## 5. Spec check on PR #133 choices

1. **Order + dedup.** Order is not meaningful for anyOf **or** oneOf/allOf (§10.2 quoted above), so positional handling of oneOf/allOf is over-strict-but-sound and anyOf-only normalisation is spec-safe. Dedup is **assertion-preserving for anyOf** (≥1 over a multiset = ≥1 over the set) and for allOf (A∧A=A) — hence language-preserving; the only residue is that anyOf requires "all subschemas MUST be examined" for annotation collection, so two identical entries can emit the same annotation twice from two schema locations (draft-bhutton §10.2.1.2), which does not affect L. **Your oneOf asymmetry is CONFIRMED**: "exactly one schema defined by this keyword's value" counts array entries, so with A present twice every instance matching A matches two branches ⇒ that oneOf accepts nothing that A accepts; dedup there turns non-matches into matches = it **widens** L and is therefore **not** language-preserving. Note the spec never uses the word "duplicate" — that is my direct application of the "exactly one" text, corroborated (search-salvaged, low confidence) by the `jsonschema` changelog folding a repeated oneOf branch because it "can never contribute exactly one match" (https://github.com/Stranger6667/jsonschema-rs/blob/master/CHANGELOG.md) and an OpenAPI discussion answer "If you have two identical oneOf options. No JSON instance that valida…" (https://github.com/OAI/OpenAPI-Specification/discussions/3608). Keep dedup to *structurally identical* branches (same JSON/`$ref`); subsumption removal (A ⊆ B) is a semantic judgement that tools only offer behind an explicit flag.
2. **anyOf ⊇ oneOf.** Yes — "at least one" vs "exactly one" (§10.2.1.2/.3; "one or more" vs "exactly one" on the combining page). L(oneOf[A,B]) ⊆ L(anyOf[A,B]), strictly iff some instance matches both branches.
3. **`1` vs `1.0` — correct.** Spec: "number: An arbitrary-precision, base-10 decimal number value, from the JSON 'number' value" and "the data model makes no distinction between integers and other numbers"; §4.2.2 instance equality: "both are numbers, and have the same mathematical value", with "mere formatting differences (indentation, placement of commas, trailing zeros) are insignificant" (https://json-schema.org/draft/2020-12/json-schema-core). `const`/`enum` only say the instance "is equal to" the value and defer to that definition (validation §6.1.2–6.1.3) ⇒ `const: 1` and `const: 1.0` are the same value. Keeping boolean distinct is likewise spec-correct (equality requires "the same type", and `true`/`false` are their own clauses). RFC 8259 §6 agrees: one number grammar, no int/float split, and only integers within ±(2^53−1) are guaranteed bit-exact across IEEE-754 implementations (https://www.rfc-editor.org/rfc/rfc8259). **Do not extend the unification to the `type` keyword**: "integer" is defined as matching "any number with a zero fractional part" (validation §6.1.1) and §7.1's foreword notes "the 'type' keyword … defines an 'integer' type which is not part of the data model" — so `type: integer` → `type: number` is a real widening.
4. **`format` — annotation by default, so admitting it is conservative tool policy, not spec.** "The value of format MUST be collected as an annotation, if the implementation supports annotation collection"; implementations "MAY still treat 'format' as an assertion in addition to an annotation … MUST provide options to enable and disable such evaluation and MUST be disabled by default", may implement it "as a no-op by always producing a validation result of true"; the Format-Assertion vocabulary is OPTIONAL, is declared `false` in the standard meta-schema, and an implementation that cannot fully validate "MUST refuse to process the schema" when it is declared true (https://json-schema.org/draft/2020-12/json-schema-validation §7.1–7.2). OpenAPI 3.1 calls format "an optional modifier property" and defines only int32/int64/float/double/password as its own additions (https://spec.openapis.org/oas/v3.1.0 §4.4). ⇒ a format-only change does **not** alter L(S) unless the schema declares format-assertion, so counting it as a bidirectional break is over-strict-but-sound; comparing format strings for *equality* is defensible anywhere, and excluding format from a union's sibling-key comparison is the position the spec actually supports.
5. **date-time — performative, never lexicographic.** RFC 3339 §5.1: string sorting gives a time-ordered sequence only "Assuming that the time zones of the dates and times are the same (e.g., all in UTC), expressed using the same string (e.g., all 'Z' or all '+00:00'), and all times have the same number of fractional second digits", and §4.2: "18:50:00-04:00 is the same time as 22:50:00Z" (https://www.rfc-editor.org/rfc/rfc3339) — so different offsets make text order ≠ instant order. JSON Schema's `date-time` is only a validity check against the RFC 3339 ABNF and format checking is explicitly "limited to syntactic checking" (validation §7.3.1/§7.2.2). ⇒ a `date-time` → `date`/`time`/other change is a real semantic shift that no text comparison can classify; leaving it as a possible break matches tool convention (undecidable → WARN), not a spec mandate.
