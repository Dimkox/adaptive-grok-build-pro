# Requirements analysis — issue #121 (durable activation probe)

Decision authority: GitHub issue #121; the user selected option 1, **make activation probes durable**. The historical 2026-09-16 values (usage 769/191, `provider_requests=1`, job ID `omni-activate-20260916-e7d0f72b`, profile digest `4cc85b8a…`) are legacy operator-attested evidence only: this change must not fabricate a row for them or imply that a new readback re-derives that old provider call.

| ID | Acceptance criterion | Evidence needed |
|---|---|---|
| TA-AC-01 | A server-executed activation probe has a durable record keyed by a caller-stable, unique probe job ID, distinct from the end-to-end pilot landing job. Record profile identity and exact profile digest, normalized outcome/state, provider request count, validated input/output usage (or explicitly unknown), HTTP status when known, bounded failure classification, timestamps/revision, and an integrity digest/version. | Store/API tests assert exact readback fields and prove probe job/usage are distinct from pilot row/usage. |
| TA-AC-02 | Probe execution is idempotent by job ID. Repeating the same command returns the existing state/observation and never dispatches another provider request; a request that reuses the ID with different profile/request identity conflicts safely. Separate IDs create separate probe records. | Fake provider call counter across retries/restart; identical retry count remains one, identity mismatch conflicts, second ID yields a second record. |
| TA-AC-03 | Lifecycle is durable before external dispatch: a record enters `pending` (or equivalent) before the provider call. A restart/interruption leaves a discoverable non-success state; recovery/read does not silently rerun the provider call. Final success/failure updates the same record with monotonic revision/transition. | Crash/reopen tests at pre-dispatch and post-dispatch boundaries; pending/interrupted readback and no second provider call. Explicit reconciliation/retry policy must preserve at-most-once dispatch for a given ID. |
| TA-AC-04 | Read-only lookup by probe ID works after process exit/restart without credentials, network access, or a provider call. It returns enough canonical persisted content to recompute/check the observation digest and to distinguish pending, successful, and failed probes. | Lookup test with provider transport configured to fail if invoked; digest recomputation and exact identity assertions. |
| TA-AC-05 | Only allowlisted, bounded facts are persisted/exposed. Never store API keys, auth headers, raw upstream response/error bodies, unvalidated draft text, or exception strings. On dispatch, `provider_requests` is exactly 1 even if response decoding/accounting fails; before dispatch it is 0. Failure records retain safe category and known status/usage semantics without falsely claiming normalized success. | Adversarial secret/body fixtures checked against DB bytes and serialized/API output; tests for pre-dispatch, transport, HTTP, malformed draft/accounting failures and request counts. |
| TA-AC-06 | Schema evolution is additive and recoverable from the currently supported DB version: existing landing jobs, commands, observations and their identities remain intact; no fabricated backfill. Fresh DB and prior-version upgrade/restart both work. | Versioned migration tests from existing schema v2 with seeded rows/commands, then reopen and compare exact prior values plus new probe operations. |
| TA-AC-07 | New successful probes retain the existing synthetic-only input boundary and profile-digest binding. They neither read project/customer input nor alter the independent end-to-end pilot job. | Existing and new provider/probe tests plus explicit database assertions for separate identities and unchanged pilot row. |

Implementation implication from source inspection: `probe_qwen()` currently returns transient facts and its CLI prints bounded output; `SQLiteLandingJobStore` is v2 and persists ordinary provider observations in `landing_jobs`. The probe path has no durable identity/lifecycle today. A durable execution path must establish job identity and pending state before dispatch; wrapping the current one-shot call and writing only after it returns cannot meet interruption or no-duplicate-call requirements.
