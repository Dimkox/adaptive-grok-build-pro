## Backup/restore scope

`factory/src/adaptive_factory/landing_backup.py::_roots(config)` returns exactly the configured landing state root, publication state root, and artifact output root. `create_snapshot()` copies `landing.sqlite3`, optional `publication.sqlite3`, and allowlisted artifact files; landing DB capture uses SQLite's backup API and includes committed WAL-visible rows. `restore_snapshot()` has a closed manifest inventory and recreates only those configured roots with live execution disabled. Thus an activation observation stored in the existing landing-job table is covered by the existing landing DB backup and same-path restore, subject to the established writer locks, digest check, and size/deadline caps.

A separate sidecar DB is **not** covered. It is absent from `_roots`, snapshot manifest categories, closed restore inventory, and restore destination validation. If implementation chooses a sidecar, the offline snapshot contract must be extended explicitly (config root and trusted-path rules, lifetime lock, manifest schema/version and category allowlist, exact DB identity/schema checks, restore path/digest validation, bounded file/aggregate I/O accounting, and backup/restore tests). Prefer the existing landing DB if its current schema can represent the observation without weakening other invariants.

## CLI and contract conventions

- `adaptive-landing-state backup --config <private-config> --snapshot <new-private-path>` requires the landing service and publication writer stopped, acquires their writer locks, and returns JSON including `status=snapshot_saved` and `manifest_sha256`. Restore requires the saved digest, stopped writers, `live_enabled=false`, and absent destination roots; it returns `restored_inactive`, never replays provider work, and does not restore the external publication pointer.
- Existing `adaptive-landing-submit status --job-id` reads the caller's failover journal. Its runbook explicitly says it is local and not a live backend poll; it should not be used or documented as the new activation-probe observation lookup unless implementation actually connects it to that record.
- `factory/README.md` currently documents the direct probe's bounded JSON: successful profile/model/digests/usage/elapsed fields, and a failed result with an allowlisted category and HTTP status only. Preserve that redaction style: no provider body, exception string, credential, or raw prompt in new operator output or durable observation fields. For a server API, document whether it is a new authenticated route or an internal operator CLI; the frozen `landing-dogfood.v1.json` currently has only submit/read/cancel/result operations, so do not imply the existing public v1 contract exposes it unless the contract is deliberately extended/versioned.
