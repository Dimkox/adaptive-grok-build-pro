# Architect analysis — contract document metadata (#120)

## Finding

The reproduction is consistent with the comparator boundary. `compare_contracts()` first short-circuits only on canonical document and reference-graph identity. For bidirectional JSON Schema comparisons, `_compare_schema_direction()` examines `$id`/`$schema` and structural constraints but does not compare `title` or `description`; therefore a non-identical document can end with `compatible` and no reasons. `event` adds a separate description-based `_event_meaning()` comparison, so the behavior is not uniform across kinds. OpenAPI has a bespoke structural walk which likewise does not generally compare prose fields (and ignores several descriptive surfaces). A fix limited to the root JSON Schema branch would leave registered contract kinds with inconsistent visibility.

There are two separate concepts that should remain separate in the API: wire compatibility and a change to normative documentation. Reusing `incompatible` or an existing wire-break reason for a prose-only diff would falsely claim a shape break; retaining `compatible` with no finding would preserve the blind spot. A distinct outcome/reason is the bounded fail-safe shape, but whether such documentation is governed is an unresolved contract-policy choice from the issue and must be named by the policy owner before implementation.

## Bounded design recommendation (pending policy decision)

Keep all existing structural compatibility calculations and statuses unchanged. Add a deterministic metadata-diff projection for *declared contract documents* and report it separately from compatibility, keyed by contract identity and stable JSON Pointer locations. Candidate surfaces should be enumerated per supported kind rather than recursively treating every string named `description` as normative: JSON Schema `title`/`description` (including nested schemas); OpenAPI schema metadata plus selected Info/Path/Operation/Parameter/RequestBody/Response/Header/Security Scheme descriptive fields; event descriptions where `_event_meaning()` already treats schema descriptions as meaning-bearing; and any genuinely supported signed-payload metadata only after confirming its document model. Include `$id`/`$schema` in the schema-policy inventory, although these are already checked structurally. Keep the projection bounded by existing parse/node/reference budgets and fail closed as unsupported when traversal is incomplete.

Expose a distinct `documentation_changed` (or equivalent review-required) signal while retaining the wire result (`compatible`, `incompatible`, `unsupported`) separately. A gate may then fail/review on governed metadata changes without mislabeling them as wire incompatibility. If the chosen policy is “explicitly non-governed,” the report must instead say `not_governed`/not-applicable and must not report a clean compatibility pass as though that metadata had been evaluated; authoring guidance should move normative constraints into machine-checkable schema keywords or other governed fields. Do not silently implement either policy.

## Compatibility and migration implications

- Existing CLI consumers, JSON reports, tests, trust/evidence projections, and downstream rule evaluators may assume the current status vocabulary. Prefer an additive field/category first; if a new top-level status is required, version the report contract and update strict parsers together. A new reason under `incompatible` alone is not semantically safe.
- Existing event checks already treat schema `description` as meaning, while JSON Schema and OpenAPI do not. Aligning all kinds may newly surface changes that were previously accepted. Inventory current registered documents and measure the diff before turning the signal into a blocking policy; do not auto-rewrite history or weaken structural rules to avoid migration findings.
- Repository metadata changes that are intentional will need explicit review/evidence, a governed allow/receipt mechanism, or conversion to structural keywords. The allow mechanism must bind exact contract ID, base/head digests, and changed metadata paths; a free-form exemption would allow prose to drift again.
- The `versioned_break` and `exact` modes need explicit semantics for documentation-only changes. Preserve their structural behavior and represent metadata review independently unless policy owners explicitly decide prose changes require versioning.
- Trust CI is separately deployed and authoritative. Local report changes cannot imply that deployed Trust CI consumes or enforces the new signal. Any external protocol change requires its own deployed-policy rollout; keep this repository change compatible with the existing exact-SHA authority boundary.

## Required contract-policy decision

Choose and record one of: (A) selected contract metadata is governed, produces a distinct review-required finding, and is blocking until evidence is supplied; or (B) metadata is explicitly outside fitness governance and the report clearly marks it not governed while guidance prohibits normative prose there. The issue expressly rejects silently choosing. Until that decision is recorded, implementation should be limited to characterization/tests or a non-enforcing additive diagnostic, and must not claim the policy gap is closed.
