# Repository exploration: `usage.reported` and migration conventions

Route `6a88338ed69e`; read-only inspection of the token-accounting repository. No product files were changed.

## Contract and event path

- The requested behavior is specified in `docs/superpowers/specs/2026-09-11-token-cache-cost-accounting-design.md`: v2 adds `cached_input_tokens`, `cache_write_tokens`, and a closed `price_table`; the server validates the SHA-256 `price_table_digest` and derives `cost_usd_micros` by floor division. Legacy v1 durable rows remain readable and are not backfilled.
- Event vocabulary/capability mapping is in `factory/src/adaptive_factory/protocol.py` (`_EVENTS`, `_CAPABILITY`, `_PAYLOAD_FIELDS`, and `validate_event_payload`). Current `usage.reported` is an exact seven-field payload: provider call ID, digest, three token categories, caller-supplied cost, and output bytes. The validator currently checks only string/int types; it does not validate digest semantics, nonnegative values, or a price-table object.
- Producers are the two adapters: `factory/src/adaptive_factory/adapters/codex.py` translates native `turn.completed` usage into `usage.reported`, and `factory/src/adaptive_factory/adapters/grok.py` translates native `usage` records. Both currently pass through provider usage (with fixed `provider_call_id="fixture-call"`), including caller-provided cost/digest fields.
- The in-process consumer is `factory/src/adaptive_factory/brokers.py`: `UsageProposal` carries the current fields; `ProposalBroker._usage` requires the same exact seven fields, validates the digest shape and nonnegative integer values, applies token/cost/output task limits, and computes `total_tokens` from input/output/reasoning. `proposal_idempotency_key` includes all current usage fields and author role, so any expanded payload must be included in its canonical body.
- The API consumer is `factory/src/adaptive_factory/api.py` `execution_usage` (v1 and v2 routes). Its closed field set currently permits the same caller-supplied `cost_usd_micros` shape, then calls `execution_proposal(..., event_type="usage.reported")`; the generic proposal path is `service.commit_execution_proposal` -> `store.commit_execution_proposal` -> SQL `factory.execution_proposal_commit`/related canonical persistence functions.
- SQL-side validation/reconciliation is in `factory/src/adaptive_factory/resources/015_execution_canonical_persistence.sql`. The usage branch validates exact JSON keys/count, digest regex, provider-call-ID length/secret pattern, numeric bounds and packet limits, builds the canonical idempotency body, and later reconciles every usage proposal against `factory.usage_observations` by provider call ID, digest, calculated token sum, cost, and output bytes. These SQL checks must be extended consistently with the v2 fields and derived-cost rules.

## Persistence and budget consumers

- The original table is created by migration `003_budgets_kills_reconciliation.sql`: `factory.usage_observations` has `observation_id`, task/run IDs, `provider_call_id`, `price_table_digest`, aggregate `cost_usd_micros`, aggregate `token_units`, and `output_bytes`, all nonnegative where numeric. It has runtime grants; later `005` adds FK/revokes and `009` adds the task/run index. Metrics trigger wiring in `012_bounded_metrics_snapshot.sql` observes inserts/updates/deletes on this table.
- The legacy direct accounting path is `factory/src/adaptive_factory/store.py:4220` `observe_usage`, exposed by `service.py:929` and `api.py:1041`. It checks provider ID and aggregate values, enforces `(run_id, provider_call_id)` idempotency, releases reservations, checks task observed limits, inserts one observation, updates task aggregate cost/token counters, and records blocked accounting. It currently has no component-token parameters and is separate from canonical execution-proposal persistence; preserve/route it deliberately when adding v2.
- Canonical completion checks in migration 015 require at least one usage observation for a completed run and ensure one-to-one proposal/observation correspondence. Task budget enforcement remains based on aggregate `cost_usd_micros`, aggregate `token_units` (input + output + reasoning), and `output_bytes`; adding cache columns should not change those aggregate semantics.

## Migration conventions

- `factory/src/adaptive_factory/migrations.py` discovers package resources named exactly `NNN_[a-z0-9_]+.sql`, sorts by version, and requires contiguous versions starting at 001. Applied rows in `factory.schema_migrations` are checked for exact version/name/SHA-256 equality; any drift fails. New schema work therefore must be a new next-number migration (currently 019), with no edits to 001–018.
- The migration runner applies each pending SQL file in one transaction under an advisory lock and 5-second local lock/statement timeouts, then records its checksum. SQL must be UTF-8 and factory-scoped.
- Existing tests (`factory/tests/test_migrations.py`) assert the contiguous version list and immutable historical tuples/checksums. The current test expects versions 1..18 and will require an intentional v19 expectation update alongside the new file.
- Recent migration style is additive/forward-only: `018_semantic_validation_bridge.sql` uses `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...`, creates new tables/functions/indexes, and explicit `REVOKE`/`GRANT` capability boundaries. Its migration test rejects `DROP`, `CASCADE`, broad `GRANT ALL`, and similarly destructive operations. The 015–017 tests likewise reject drops/deletes and assert execution-contract shape.
- For this change, the plan explicitly calls for `factory/src/adaptive_factory/resources/019_usage_token_components.sql` with nonnegative cache-token columns, `NOT NULL DEFAULT 0`, no historical rewrite/backfill, and compatibility for old readers. A migration test should assert the new file is version 019, additive, and contains the expected defaults/checks while preserving the existing role boundary.
