## Recommendation and meaning of a pass

Keep the existing top-level `schema_version: 1` and `status: pass|fail`. Add a required `product-coverage` check and additive `product_coverage` metadata. A complete, applicable change inventory with an uncovered relevant consumer path produces `fail` and code `incomplete_product_coverage`; an honestly empty/non-product scope can produce `skip`. Optional unrelated checks remain optional. Do not introduce an overall `incomplete` enum, a checker registry, a dependency, or native-language execution for this repair.

The useful minimum is **at least one meaningful, actually applicable check for each relevant changed path**, not every optional analyzer and not merely one checked file of the same language. A successful Bandit scan of `src/a.py` cannot qualify `engineering/b.py`; a successful stack suite cannot qualify `App/Main.swift`. A checker can find defects while establishing that its scope was actually reached: the original failed checker must keep the overall run failed. Coverage completeness is distinct from cleanliness, rule completeness, behavioral test coverage, and merge approval.

This permits a normal Python consumer with actual successful Bandit file records to pass while preserving missing optional Ruff as a skip. It requires excluded `engineering/*.py` and unsupported Swift product changes to remain non-green. Do not add an unconditional Python syntax fallback merely to turn those excluded-file cases green: that would change the accepted meaning of this slice.

## Scope inventory and exclusions

Retain the existing report `changed_files` and `changed_file_inventory` shape, adding completeness, bounded reasons, and path provenance. A small verifier-specific helper can return the same tuple plus additive metadata; leave the public fingerprint `changed_files()` contract unchanged unless a separately justified change is necessary. Reuse the actual delivered bounded Git/process helper when available rather than copying unpublished doctor/lifecycle code.

1. Collect the union of each already selected route/PR base, staged, unstaged, and untracked paths. Record which source observed each path and whether that source completed. Untracked output failure, malformed NUL records, unavailable/ambiguous range, timeout, or an exhausted budget is `unknown/incomplete`, never zero. An unborn Git repository can use complete index plus untracked results; a non-Git tree needs an explicitly bounded fallback or an honest unavailable result.
2. Preserve exact filesystem identity via NUL bytes and filesystem decoding. Do not normalize a literal POSIX backslash into a separator or use `splitlines()` for path transport. Reject escaping/absolute path records; display escaped, bounded relative witnesses rather than raw terminal control bytes. Do not read secrets or file contents during path inventory.
3. Keep changed tracked files even under a vendor/cache/build/ignored-looking prefix. Git ignore is an untracked-enumeration policy, not permission to discard tracked product changes. Known untracked runtime/cache noise can keep the existing proven-untracked exception and an explicit reason. A failed index query destroys that proof.
4. Keep deleted paths and both rename endpoints in inventory. Surviving destinations get normal obligations. A deletion has no current file to lint: report `deleted_source` rather than claiming a successful nonexistent-file scan. A deletion-only product change needs an applicable project-level validation fact; absent that, disclose the unsupported obligation. Missing, unreadable, special, or symlinked relevant paths are not silently non-product and must not cause traversal outside the root.
5. Separate source, configuration, resource, documentation/workflow evidence, and unclassified paths. This is a visible finite policy, not a configurable checker registry. Source recognition must run before any documentation-directory exemption; there must be no blanket `engineering/`, `scripts/`, `tests/`, `factory/`, or hidden-directory exclusion. Unknown candidate languages from #157 stay visible. Resources such as `.tmx` and product `.png` do not become Swift-checked simply because a Swift source was inspected.
6. Documentation/workflow-only changes can be outside product-check obligations with an explicit reason; this does not imply whole-repository product validation. A clean diff in a Swift repository need not fail solely because Swift exists. State that the new result concerns this inventory, not the whole untouched application.
7. Path origin labels are observational. Exact-path intersection is sufficient to prevent stack checks from covering unrelated consumer files; no installer origin registry or blanket source-repository exemption is needed. In this repository the stack's own modules are product code.

Suggested bounded starting contract, to freeze before implementation: at most 8,192 unique change paths, 1 MiB stdout per Git query, 16 KiB diagnostic stderr, 20 seconds shared inventory work deadline with each command at most 3 seconds/remaining budget; maximum 32 displayed witnesses with 240 escaped characters each and 32 KiB new diagnostic rendering. These are proposed engineering limits, not measured scalability claims. Budgets must apply during capture/enumeration, not after an unbounded capture. Exact internal path identity must not be shortened for matching. A hit records its reason and prevents a complete claim; existing discovered relevant paths are retained. Reuse predecessor helpers only after their actual delivery and inspect their cancellation/cleanup contract.

## Analyzer facts: proposed inputs are not inspected files

The docs analyst inspected the pinned tool implementations without execution; their report should be the primary-source reference for these details.

- **Ruff:** `--show-files` is candidate discovery, uses newline/lossy text, flattens discovery errors, and does not account for later `lint.exclude`. Diagnostics JSON, statistics, and SARIF do not enumerate clean inspected files. Direct file arguments bypass exclusion rules unless force-exclude applies; unreadable-file failure depends on E902. Do not call discovery output `scanned`, force exclusions off, override rules, scrape debug logs, or reimplement arbitrary Ruff configuration. Preserve existing invocation behavior and genuine failure. Report an unproven scope as such, with candidate counts only when their encoding and completeness are established.
- **Bandit:** request supported JSON from the real invocation, preserving the current consumer config and exclusions. File metrics minus `errors[].filename` can establish a successful file parse/scan; `_totals` and aggregate LOC cannot. File metrics begin before parsing, so metrics alone are insufficient. The docs analyst also found caught plugin exceptions that can exist only in stderr: internal-error diagnostics or incomplete/truncated diagnostic capture must disqualify an otherwise positive scope record. Ordinary nosec warnings need a positive control so they are not blindly made failures. Normalize only safely root-bound exact names; reject malformed, outside-root, duplicate/ambiguous records, or unresolved byte identities rather than matching a lossy spelling.
- **Python input expansion:** add bounded relevant changed Python files to the existing candidate input set for Bandit so normal consumer `src/app.py` has a usable path to coverage. Preserve tool exclusions and source/test policy. An excluded `engineering/app.py` must remain absent from successful metrics and fail the aggregate; do not override exclusions or count the requested argv member. Empty/syntax-error/unreadable/private fixture cases must prove the chosen Bandit semantics on the actual pinned executable when the lane opens.
- **PHP and small built-ins:** successful exact PHP lint can establish syntax coverage for the actual file. Contract parsing and SQL safety can record their exact loop membership and limited kind. None qualifies unrelated code or resources. Keep syntax/parse failures and existing security failures authoritative.
- **Opaque project commands:** an existing npm/test/Composer command can be recorded as executed with consumer-declared command provenance, but exit zero alone is not an actual file manifest. Do not invent a new user-command adapter or execute Swift/Xcode/build scripts to make detection succeed. Unsupported Swift/Apple paths should name the missing applicable checker, platform/toolchain boundary, and next action without claiming that simply finding `swift` on PATH would suffice.

Known-empty checks should report explicit not-applicable/empty scope, not a content PASS from scanning nothing. If relevant paths exist and that empty checker was their last possible evidence, the aggregate fails. A tool with unknown scope is different from known-empty; retain its execution outcome and say scope is unproven rather than inventing a zero count. One optional analyzer's exclusion does not itself force failure if another suitable checker actually inspected that exact path.

## Compatibility point that must be resolved before implementation

The desired positive Python consumer, excluded engineering negative control, and unsupported Swift negative control can be implemented using the facts above. A fully general per-file rule also encounters **this repository's test/helper files**: Bandit and Core coverage exclude them, and unrestricted Ruff lacks an actual inspected-file manifest. A root-wide rollout cannot pretend those files are proven, blanket-exempt the tests directory, or adopt a syntax fallback that invalidates the required engineering exclusion control. The writer must not discover this only during a nine-minute full gate.

The bounded choices are (a) qualify a narrowly documented actual Ruff input contract without changing consumer exclusions, with positive and exclusion/error controls; or (b) obtain genuine invocation-owned per-file execution facts for validation code from the existing runner, with unexecuted/missing helpers retained as unproven. This is a source-design choice for the coordinator to resolve from the other analyses before dispatch, not a request for a new user permission or a basis to fabricate green evidence. If neither is possible within the chosen slice, narrow the claimed completed scope explicitly and keep the remaining acceptance criterion/issue open. Do not deploy a universal unknown-to-fail switch as the entire fix.

## Additive report contract

Keep CheckResult fields/statuses and existing report fields compatible. Add `product_coverage` with a nested version and:

- inventory source/ranges, completeness, finite reasons, limits actually hit, and relevant/non-product/deleted/unclassified counts;
- checker observations distinguishing `proposed`, `selected`, `processed`, and `unknown`, command/config provenance, completion, and observed file identities or a bounded content-addressed manifest;
- exact relevant-path obligations and their qualifying check references, plus bounded uncovered witnesses and full counts;
- `state: complete|incomplete|not_applicable` solely inside this new metadata, never as receipt/overall status;
- an explicit limited meaning, e.g. static syntax/security checks of these changed paths, not whole-product or behavioral coverage percentages.

In ordinary CLI output the `product-coverage` summary/details must show the incomplete reason, relevant/checked/uncovered counts, and a concrete remedy; users should not need `--json` to discover the gap. Use existing string-valued `details` entries for reason code/path/message. The whole report already flows into receipt details; preserve no-record, cancellation, negative receipt, source-stability, and exact fingerprint binding from the delivered predecessor.
