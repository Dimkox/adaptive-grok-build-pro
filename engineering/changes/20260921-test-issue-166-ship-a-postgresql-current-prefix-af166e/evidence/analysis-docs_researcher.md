## PostgreSQL documentation ruling

[PostgreSQL 17 CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html) says `CREATE OR REPLACE FUNCTION` preserves existing ownership and permissions and is distinct from drop/recreate. A `pg_proc` OID and effective ACL check before/after migration is a useful regression; [pg_proc](https://www.postgresql.org/docs/17/catalog-pg-proc.html) documents `proacl`. [PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) describes `ACCESS EXCLUSIVE` as a **table-level** mode, but does not state that `CREATE OR REPLACE FUNCTION` takes it on the function or waits for an executing call. Therefore the issue's asserted lock mechanism is unverified and should not become a test oracle. [PostgreSQL 17 client settings](https://www.postgresql.org/docs/17/runtime-config-client.html) says `lock_timeout` applies to each lock attempt and `statement_timeout` to each statement; equal 5-second settings do **not** guarantee a 5-second bound for the entire migration transaction.

## Test mapping and negative controls

1. In a disposable database, apply the checkout's actual resources `001..N-1`, inserting the exact `version/name/sha256` rows into `factory.schema_migrations` as existing historical tests do. Capture the target function's `regprocedure` OID, `proacl` or effective EXECUTE matrix, and pre-upgrade behavior. Run the real migrator once; assert only resource `N` is returned, the final row equals `discover_migrations()[-1]`, no earlier row changed, OID and intended grants remain, new behavior is present, and a second `apply()` returns empty. Derive `N` from `discover_migrations()`; an explicit assertion that the current last resource replaces this function will prevent a future unrelated migration from silently changing what the test means.
2. Add a drift negative control by modifying one recorded prefix checksum in the disposable database; expect `MigrationError`, no `N` row, and unchanged function identity/behavior. Restore only within the owned fixture or discard its database.
3. Exercise two concurrent sessions with a bounded future/deadline and an explicit release in `finally`. One may execute the old function while another applies `N`; assert observed completion/rollback and no hung session, without requiring an unproven function lock conflict. For a deterministic timeout path, a separate session can hold a conflicting lock on `factory.schema_migrations`, which `apply()` reads; assert failure rolls back the `N` row and function body, then release and retry. A wall-clock deadline belongs to the test harness because server timeouts are per statement/lock attempt.
4. Keep `001..021` SQL and production timeout settings immutable. Existing privilege-matrix assertions in `test_postgres_integration.py` are useful precedent, but this test needs a before/after comparison around the incremental apply. Use `factory/tests/test_execution_persistence_postgres.py` and its disposable database helpers or an equivalent isolated fixture. Avoid hardcoded global migration count/digest; `run_disposable_exit.py` itself has no count pin, while some fixed historical tests deliberately pin a version.
