## PostgreSQL semantics and bounded ruling

PostgreSQL 17 documents preservation of ownership and permissions with `CREATE OR REPLACE FUNCTION`; drop/recreate makes a different entity. [CREATE FUNCTION documentation](https://www.postgresql.org/docs/17/sql-createfunction.html).

The PostgreSQL 17 implementation opens `pg_proc` with `RowExclusiveLock`, updates the existing catalog tuple, and explicitly preserves `oid`, `proowner`, and `proacl`. This supports measuring OID/ACL preservation; it does **not** support the issue's assertion that a running function call necessarily forces an ACCESS EXCLUSIVE wait. Do not encode that assertion or describe an idle transaction after a function call as “holding the function lock.” [PostgreSQL source, ProcedureCreate](https://raw.githubusercontent.com/postgres/postgres/REL_17_STABLE/src/backend/catalog/pg_proc.c).

Use the actual migrator advisory lock for deterministic contention: PostgreSQL documents that transaction advisory locks conflict with the same identifier and release at transaction end, with observable entries in `pg_locks`. [Advisory lock documentation](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS).

Timeouts are per statement/acquisition, not an overall five-second apply transaction budget. With equal limits the documentation says statement timeout triggers first; assert bounded server cancellation and accept the corresponding timeout SQLSTATE rather than matching only “lock timeout.” Accepting only `57014` and `55P03` is a reasonable narrow portable timeout assertion; do not swallow other database failures. A client `FutureTimeout` is a test failure, not evidence of the server timeout. [Timeout documentation](https://www.postgresql.org/docs/17/runtime-config-client.html).
