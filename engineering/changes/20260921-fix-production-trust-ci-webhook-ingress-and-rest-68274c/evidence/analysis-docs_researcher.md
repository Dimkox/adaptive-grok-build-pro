# Docs researcher analysis — Trust CI ingress

## Established host and source facts

The sibling measured `check170-observation.md` report in the issues-wave worktree reports a healthy API only on host `127.0.0.1:18080`, while Tailscale Serve in namespace `vpn` targets `10.200.200.1:18080` and receives connection refusal. Public GET returns 502; the loopback webhook GET returns the expected 405. The host has `veth-vpn-h` UP at `10.200.200.1/30`; `ip route get 10.200.200.1` resolves to `lo`, and the peer route `10.200.200.2` resolves to `veth-vpn-h`. `systemd 255.4` and `/usr/lib/systemd/systemd-socket-proxyd` are installed. This analysis made no network or service changes.

## systemd 255 configuration semantics (installed manual pages)

- `systemd-socket-proxyd(8)` accepts an inherited listening socket with `Accept=no`, opens one outgoing connection per client, and forwards bytes bidirectionally. A socket unit with `ListenStream=10.200.200.1:18080`, `BindToDevice=veth-vpn-h`, and `Accept=no`, paired with a same-name service executing `/usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:18080`, matches its documented pattern. `systemd.socket(5)` says `BindToDevice=` uses `SO_BINDTODEVICE` and adds implicit `BindsTo=`/`After=` on the device unit; the listener accepts only packets received on that interface. Use a concrete IPv4 listen address, not bare port 18080, to avoid wildcard/IPv6 publication. Confirm the device unit name and socket bind at activation. `FreeBind=yes` can allow starting before the address exists but does not override the device dependency; it is unnecessary for the observed UP address and may hide a topology error.
- `systemd.resource-control(5)` says an `IPAddressAllow=`/`IPAddressDeny=` list on the **socket** applies to inherited listening sockets, while lists on the **service** apply to sockets the proxy creates. If the feature is effective, socket inbound should permit only VPN peer `10.200.200.2/32` and service egress should permit only `127.0.0.1/32`, each with deny-any. A service-only inbound list does not protect an inherited listening socket; a socket-only list does not constrain the proxy's outbound connection.
- The same man page explicitly warns IP address lists can have **no effect** without eBPF cgroup support. Installed `systemd --version` reports `-BPF_FRAMEWORK`; therefore these directives cannot be counted as an enforced security boundary from unit text alone. Do not treat `systemd-analyze verify` or parsed properties as proof of packet filtering. The host has `nft` 1.0.9, a possible kernel filtering alternative, but this unprivileged analysis could not inspect its effective rules (`nft list ruleset`: `Operation not permitted`). An operator must establish and inspect an effective, persistent input rule for this destination/port that drops packets unless ingress is `veth-vpn-h` **and** source is the verified namespace peer; check actual peer address first. Existing firewall ordering/management must be reviewed. If no enforceable and testable source restriction exists, leave the bridge socket disabled and report the ingress repair blocked.
- `systemd.exec(5)` says `DynamicUser=yes` gives a transient unprivileged identity and implies `NoNewPrivileges=yes`, `ProtectSystem=strict`, and `ProtectHome=read-only`; explicit `ProtectHome=yes` can hide home paths further. This proxy requires no host files or keys, so these are appropriate service hardening, subject to an activation test. `PrivateNetwork=yes` creates a new namespace with its own loopback. Since the destination `127.0.0.1:18080` is the **host** loopback, the proxy service must remain in the host network namespace; do not copy the manual's `PrivateNetwork=yes` example, which assumes the backend joins that same private namespace. `BindToDevice=` belongs on the socket, not as a substitute for the service's outbound controls.

## Acceptance and negative controls for the implementation/operator plan

1. Before enabling, prove `veth-vpn-h` still owns `10.200.200.1/30`, the VPN peer is `10.200.200.2`, the API remains listening only at `127.0.0.1:18080`, and the chosen kernel source filter is installed and effective. Inspect the live units and listener after activation. Verify the bridge is absent when the new socket is stopped; rollback is stop/disable only the new socket/service plus removal of its dedicated filter rule.
2. Probe from the **VPN namespace** or through Tailscale Serve: bridge `/health/ready` should return 200 and GET `/webhooks/github` should return 405; public HTTPS GET should then return 405 rather than 502. A host-local GET to `10.200.200.1` is an invalid positive oracle with `BindToDevice=veth-vpn-h`: local routing sends it over `lo`, which the bound socket excludes. The old host-loopback health probe should remain 200.
3. Prove a packet from a different interface/source cannot reach the new listener, and prove a packet from the actual VPN peer can. If ingress source testing cannot be performed, packet filter enforcement remains unproven. No synthetic webhook POST or GitHub event replay is needed for this bridge check. After it is live, inspect GitHub's real delivery receipt and exact PR #170 Check Run separately; bridge health alone does not prove a webhook was delivered or a job queued.
