# Architect analysis — Trust CI webhook ingress, route 68274cb876e4

## Measured cause and desired boundary

The September 21 observation establishes a healthy API at host `127.0.0.1:18080`, a Funnel upstream of `10.200.200.1:18080`, host `veth-vpn-h` carrying `10.200.200.1/30`, and `tailscaled.service` running in `/var/run/netns/vpn`. The public webhook GET returned 502, the loopback webhook GET returned its expected 405, and no webhook POST reached the API during the observed PR #170 window. The namespace's `127.0.0.1` is distinct from host loopback, so changing Funnel to loopback does not solve this mismatch. The proposed repair is a host-namespace listener on the exact veth address and port, forwarding to the unchanged loopback API.

## Smallest reversible host design

Prepare two source-controlled example units for an operator-reviewed host installation, named `adaptive-trust-ci-webhook-bridge.socket` and `.service`. The socket uses `ListenStream=10.200.200.1:18080`, `Accept=no`, and `BindToDevice=veth-vpn-h`; the service uses the present `/usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:18080` in the **host network namespace**. Enable/start only the socket; the service is socket-activated. Keep the Docker API publish at `127.0.0.1:18080`, Tailscale Serve upstream/path, webhook verification, and all Trust CI containers/configuration unchanged. Harden the service with no new privileges and a read-only filesystem; do not use `PrivateNetwork=` or `NetworkNamespacePath=` because it must reach host loopback.

Prerequisites before operator installation: verify `veth-vpn-h` and `10.200.200.1/30` still exist, the VPN peer's actual source address, port 18080 is unused on that address, the proxyd binary path, and the systemd unit that creates the veth/assigns its address. Bind the socket's lifecycle after that existing network setup and to the veth device; do not invent a network unit name. `FreeBind=yes` may handle the address-assignment race after the device exists, but requires review with the actual host systemd behavior. If the device can disappear and return, provide explicit restart/re-activation through the existing network setup unit; a one-time `After=` order does not prove recovery. Fail closed if prerequisites are missing rather than widening the listener to `0.0.0.0`.

Restrict ingress to the verified VPN peer on `veth-vpn-h` with an exact host firewall/interface rule or an equivalent measured restriction. Binding to `10.200.200.1` alone limits destination but does not prove source restriction. `systemd-socket-proxyd` is a TCP bridge: it forwards **all HTTP paths** to the API for a peer that can reach the socket. The public Funnel path mapping must remain `/webhooks/github` only; the VPN peer itself gains network reachability to other API paths, which is the material new exposure requiring security review. Existing server-side webhook HMAC and endpoint authorization remain the enforcement boundary.

## Activation evidence and rollback

Stage the units and exact peer restriction, then have the authorized host operator start the socket. Check its bind/interface/source restriction, host loopback readiness 200, and a VPN-namespace or Funnel request to `/webhooks/github` returning 405 for GET. A host-origin GET to `10.200.200.1` may be misleading when `BindToDevice` rejects loopback-routed traffic. Public `/health/ready` should remain unavailable through Funnel; a real GitHub delivery receipt for the exact PR event should show successful POST intake, followed by the durable job and App-owned policy-epoch Check Run on that head. Do not infer those later facts from a 405 probe, GitGuardian, or worker uptime.

On failure, stop/disable only the new socket and service and remove its narrow firewall rule, restoring the observed public 502 while preserving loopback API readiness. Log unit state, listener address, HTTP statuses, and GitHub delivery/job identifiers without payloads or secrets. This design changes only the host bridge resources; it grants no authority to alter deployed API, policy, holdout, images, keys, GitHub App settings, or branch protection. The route's scope/design and production-action gates still apply to the concrete host operation despite the user's broad request to finish the work.
