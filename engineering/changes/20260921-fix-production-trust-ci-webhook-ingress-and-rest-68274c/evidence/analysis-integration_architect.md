# Integration architect analysis — Trust CI webhook ingress

## Measured failure and trust boundaries

The dated PR #170 observation supplied with this change measured a ready API on host `127.0.0.1:18080`, while Tailscale Funnel's `/webhooks/github` target was `10.200.200.1:18080`, where TCP connection was refused. The public GET returned 502; the corresponding loopback webhook GET returned its expected 405. The API Docker access log had no webhook POST in the observation window. This proves a transport break before API authentication, while GitHub's actual delivery attempt and any durable job remained unobserved. `trust-ci/compose.yaml` intentionally publishes container 8080 only on host loopback; changing it to a wildcard listener would expand the API surface.

The boundaries are: GitHub HTTPS → Tailscale Funnel's **existing `/webhooks/github` path handler** → VPN namespace/veth peer → host `10.200.200.1:18080` → host loopback `127.0.0.1:18080` → Trust CI API. The API reads the raw request body and verifies `X-Hub-Signature-256` with HMAC before parsing/enqueueing (`api.py`, `webhooks.py`); repository policy then binds permitted repositories. `systemd-socket-proxyd` is a bidirectional socket forwarder, not an HTTP router or authentication layer, per [systemd's own manual](https://github.com/systemd/systemd/blob/main/man/systemd-socket-proxyd.xml). This makes a host-side relay suitable for preserving the request bytes but incapable of filtering API paths by itself.

The same API also exposes `POST /approvals` and authenticated `/jobs/{id}`, `/attestations/{id}`, and `/metrics`; its ready endpoint discloses policy/status metadata. The new TCP listener therefore gives any caller that reaches the veth endpoint access to the *whole* loopback API. Keep the public Funnel handler scoped to `/webhooks/github`, and independently restrict the bridge's ingress to the actual VPN veth interface and peer address. A public wildcard or alternate Funnel handler must not be added. The relay needs no webhook secret, GitHub App key, approval key, CI signing key, policy, or trust-store mount.

## Minimal reversible repair

Review a paired host systemd socket/service: `Accept=no`, exact `ListenStream=10.200.200.1:18080`, `BindToDevice=veth-vpn-h`, and `systemd-socket-proxyd 127.0.0.1:18080` as the only forwarding target. Verify the observed interface and peer address at deployment rather than hard-coding an unmeasured peer IP; apply a peer-source allow rule at the socket/host firewall boundary and confirm it rejects non-peer sources. [systemd.socket](https://github.com/systemd/systemd/blob/main/man/systemd.socket.xml) documents that `BindToDevice=` binds ingress to a named interface and creates device dependencies. Do not set `PrivateNetwork=yes` on this proxy service: it must reach the *host* loopback listener, not a new private loopback. Keep the Compose API binding, Tailscale handler/target, Docker containers, deployed policy, holdout, and credentials unchanged. Socket activation and its service should have their own status/logs so transport failure is distinguishable from API/worker failure.

Stopping and disabling only the added socket and proxy service is the rollback. The loopback API must remain healthy after rollback; the public webhook returns to its prior failed ingress state, while branch protection continues to block an unverified PR. The bridge is a reachability repair, not a substitute for the App-owned exact-head check or signed approvals.

## Acceptance and negative controls

1. Before activation, record the three-way baseline: host loopback ready GET 200, host/veth bridge connection refusal, and public webhook GET 502. Unit-file/static checks should reject wildcard `ListenStream`, target other than `127.0.0.1:18080`, `PrivateNetwork=yes`, and any alteration of the Compose loopback port. A temporary local byte echo fixture can check transparent forwarding without a webhook, secret, or live API write.
2. After activation, verify the bound listener exists only at `10.200.200.1:18080`; from the VPN peer, bridge ready GET is 200 and bridge webhook GET is 405. Public webhook GET is 405, showing the same POST-only API route is reachable. Loopback remains 200. Check a non-peer source cannot connect to the bridge. Use bounded requests and record only status/latency/path, never bodies or authorization headers.
3. Probe public GETs for `/health/ready`, `/approvals`, `/jobs/nonexistent`, `/attestations/nonexistent`, and `/metrics`: none may be forwarded to the API or disclose an API response. Check the actual Funnel handler remains path-only. A relay cannot enforce this negative control; Funnel configuration must. Do not publish `/approvals` or an API root handler.
4. Inspect a **real GitHub App delivery receipt** for the relevant PR action (`opened`, `synchronize`, `reopened`, or `ready_for_review`; source supports all four). Correlate delivery ID/time with API access-log POST status, durable job identity, and the App-owned check on the exact PR head. Do not create a synthetic webhook, obtain an HMAC secret, or infer queue success from the GET probes. A 405 proves reachability only; an accepted POST plus job proves enqueueing; the exact-head App Check Run proves the worker/publisher path.
5. Test restart/recovery of the new socket/service and API-unavailable behavior separately: relay failure should be visible through unit status and public 502/connection failure, without changing the API or policy. If a public private route becomes reachable, or the bridge binds outside the veth address/peer, stop the new socket immediately and verify host-loopback readiness and the original public failure state.

Failure localization: public 502 with healthy loopback indicates Funnel/bridge; public 405 with no real POST indicates GitHub delivery/configuration; POST 401 indicates HMAC/body mismatch; accepted POST with no job/check requires authorized queue/worker inspection. Neither GitGuardian nor a ready API satisfies the exact-SHA merge gate. This report is source and prior-observation analysis only; no host operation, credential read, webhook submission, tests, or deployment was performed.
