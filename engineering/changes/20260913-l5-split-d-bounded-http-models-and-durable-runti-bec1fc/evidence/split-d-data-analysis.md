## Ownership order and recovery semantics

In live mode `compose_server_landing` validates private roots and the exact source before acquiring model credentials. It acquires SQLite's nonblocking lifetime writer lock before constructing `PrivateLandingBlobStore`. That matters because the blob-store constructor invokes `_sweep_startup_orphans`, which can delete recognized owned quarantine blobs and temporary files. A losing writer must fail with `store_writer_active` before it can enter either SQLite interrupted-job recovery or quarantine cleanup. Credentials are acquired only after ownership and blob construction.

The lock descriptor uses `O_NOFOLLOW`, `O_CLOEXEC`, mode 0600, a regular-file/owner/link-count/mode check, exclusive nonblocking `flock`, and post-acquisition inode/device comparison. Its descriptor remains live until the SQLite connection is closed. The lock is cooperative and per state root; it does not make raw SQLite clients participate, and it does not coordinate two different state roots accidentally configured to share a quarantine directory. The operator deployment still owns the one-runtime/one-state-and-quarantine pairing. Preserve the supported local-filesystem assumption rather than claim distributed locking.

SQLite constructor recovery moves accepted jobs to `needs_human/input_unavailable_after_restart`, normalizing jobs to `needs_human/provider_outcome_ambiguous`, and generation/evaluation jobs to `needs_human/local_run_interrupted`; it does not automatically repeat a model request. Failed later composition can therefore leave legitimate bounded recovery state changes even when it releases its lock. Restart must not be described as read-only or transactionally undoing all startup activity.

For an already-returned store, `close()` is idempotent and its nested `finally` releases the descriptor even if passive checkpoint or connection close raises. `compose_server_landing` catches `BaseException` after the returned store is assigned. Existing `server.build_app` closes its owned runtime after application-construction failures and in the wrapped ASGI lifespan's `finally`. These are the ownership seams that D should test directly, independently of E's dedicated host.

## Precise frozen-source limitation requiring attention

The frozen constructor does **not** guarantee release for every startup failure. After `_acquire_writer` returns, its configuration/schema/recovery block catches `Exception`, not `BaseException`. A `KeyboardInterrupt` or `SystemExit` from `_configure`, `_initialize_schema` or `_recover_interrupted` can escape before `compose_server_landing` assigns `owned_store`; that outer cleanup sees `None` and cannot close the descriptor. The same constructor's ordinary-error cleanup calls `connection.close()` before descriptor release without an enclosing `finally`, so a close error can interrupt that release. This is an actual source-control-flow gap introduced with lifetime descriptor ownership, not a tested runtime failure in this read-only analysis. The descriptor closes on process exit, but a surviving process that catches the exception can retain the writer lock and refuse subsequent startup.

Before claiming comprehensive startup/error ownership, the sole writer should add a focused failure-injection test for interruption during SQLite initialization and for connection-close failure during constructor unwind, observing whether a fresh owner can acquire the lock. If those cases are intentionally outside this exact extraction, record them explicitly as residual limitations; tests that only fail blob construction cannot establish the stronger claim. Any repair belongs to the selected sole writer and must be separately disclosed as a deviation from frozen source, then receive the route's verification and reviews. No schema migration is needed to address this lifecycle issue.

## Rollback, observability and operational boundaries

D can roll back to C's dual-reader code without a schema downgrade or persisted-envelope rewrite. Stop the owning runtime first; preserve the SQLite database together with the state needed by its WAL and retained artifact files. The advisory lock file may remain on disk and is not itself evidence of an active owner; ownership is the live OS lock. Rolling back before C requires a consistent pre-v2 snapshot or keeping a v2-capable reader. Never relabel v2 evidence as v1 or automatically replay ambiguous provider outcomes.

Rolling back to C also removes the cooperative lifetime lock behavior, so the one-process operational constraint must remain explicit during that rollback. New D code should not run concurrently with an old process that ignores the lock. No production deployment or live data action is part of this extraction, and there is no migration/external-write action to authorize merely because the data route selected its generic human gate.

Existing bounded error codes provide the immediate signals: `store_writer_active` for contention; `store_lock_file` for invalid/replaced lock; `store_open`, `store_schema`, `store_integrity`, `store_wal`, `store_sync`, `store_foreign_keys` for startup failure; and persisted `needs_human` reason codes for interrupted or ambiguous work. Use these existing signals without logging credentials, source payloads or retained evidence bodies. No new metrics pipeline, database, service or data migration is justified by this slice. Full route verification and the independently selected data/security/release reviews still determine actual D completion.
