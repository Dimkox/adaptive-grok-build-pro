# AI architecture analysis: Qwen to Grok fallback

- Route: `24b49d0529c8`.
- Baseline: `7b147366a1f9b7e4b59f17e10283cc8ad67ba0c8`.
- Scope: design only. This report is the only file written by this agent. No product changes, credentials, provider calls, installation, or operational activation.
- Status: proposed design for the named `scope_and_design_approval` gate, incorporating the controller's conservative reconciliation ruling.

## Recommendation

Use one durable normalization coordinator with exactly two ordered provider slots: primary `qwen-intl` / `qwen-plus`, then secondary `grok-vision` / `grok-4.6`. Its initial input capability is the intersection of these profiles: text and DOCX. Each slot can dispatch at most once for the same tenant, repository, job, input digest, and pinned plan. Successful Qwen normalization ends provider selection; renderer, evaluator, persistence, or publication failures must never trigger Grok.

The fallback decision must consume a typed, persisted attempt result. It cannot consume the existing generic `http_outcome_unusable`, HTTP status from the landing application alone, or exception text. Only the original validated source goes to Grok; neither a failed Qwen response nor Qwen reasoning becomes a new prompt. Both providers retain the same source-data boundary, draft schema, no-tools policy, and exact model checks.

## Observed implementation boundaries

1. `landing_live_executors.py:266–267` discards every non-200 provider HTTP status into `executor_http`. `:291–294` discards transport-stage distinctions into `executor_deadline` or `executor_transport`.
2. `_decode_response` combines wrong model, refusal, unauthorized tool output, nonterminal completion, and malformed response into broad errors. Its current valid Grok reasoning reconciliation and post-response aggregate output cap must remain intact.
3. `landing_http.py:253–265` catches executor and draft-decoder failures together, discarding already validated usage when only draft parsing fails. `_terminal` generates zero counters and a synthetic response digest. Those legacy records mean unavailable usage; they are insufficient for a two-provider accounting ledger.
4. `landing_service.py:394` requires selected evidence to match one configured profile. A chain cannot return Grok evidence under the Qwen profile or replace the selected provider identity with a generic chain name.
5. `landing_sqlite_store.py` version 1 stores one provider evidence digest and no per-provider attempt journal. `_recover_interrupted` changes `normalizing` to `needs_human / provider_outcome_ambiguous`; current recovery does not resume inference. The application purges submitted source after processing.
6. Existing retained artifacts carry one selected `LandingProviderEvidenceV1/V2` and require profile consistency. Preserve that evidence as the actual winning provider and add a separate selection record.
7. Public v1 views do not expose the failure/provenance needed by a router, as confirmed by the controller. Adding a router around those unchanged views cannot safely establish fallback eligibility.

## Failure eligibility taxonomy

Use closed enums and allowlisted reason codes generated by trusted adapter logic. Keep a failure category separate from dispatch state and usage status. Provider error bodies are bounded, untrusted data: extract only reviewed machine codes; do not persist arbitrary messages or use their prose as routing instructions. A policy/refusal classification overrides an otherwise eligible HTTP status.

| Failure | Grok eligibility | Accounting and recovery |
| --- | --- | --- |
| Primary worker/socket absent or connection refused before submitting the normalization command | Eligible | Persist `not_dispatched`; consume the primary plan slot, with zero external calls proven. |
| Definitive provider connection failure before sending HTTP request bytes | Eligible | Record `not_dispatched` only where the adapter can prove that stage; otherwise classify as unknown. |
| Confirmed provider 401, 429, or 5xx, with no policy/refusal marker | Eligible | Keep exact bounded status and safe code. Provider-specific credential/rate/service failure does not alter application authorization. Usage remains unknown unless explicitly validated. |
| Known terminated attempt deadline reported durably by the worker | Eligible under the reviewed bounded policy | Record deadline, terminal local execution, and unknown upstream usage. Local termination does not establish that the provider performed no billable work. |
| IPC connection loss after submission, worker response lost, or restart with an in-flight attempt | Reconcile first | Read the existing attempt by stable identity. Do not resubmit Qwen or infer a failure from the router timeout. If outcome cannot be established, stop `needs_human / provider_outcome_ambiguous`; do not automatically start Grok. |
| Explicit model refusal, content-policy/moderation rejection, `content_filter`, or equivalent reviewed code | Ineligible | Preserve refusal category and any factual usage. Do not seek another provider to bypass the decision. |
| Application authorization failure, cancelled/expired job, source/profile/model mismatch, unsafe input, invalid media, local budget denial | Ineligible | These are shared authorization, integrity, or request constraints, not Qwen availability. |
| Unexpected tool/function output, contradictory usage, exceeded acceptance bound, malformed/oversized provider envelope | Ineligible in initial policy | Preserve facts that independently validated; classify as protocol/accounting failure, not availability. |
| Empty/truncated completion, invalid draft fields/sections, or output-schema failure | Ineligible in initial policy | These are distinguishable model-output failures. Retain valid usage before draft rejection. A later approved policy can explicitly allow selected structural cases; do not enable all contract exceptions implicitly. |
| Unclassified 4xx, ambiguous 403, unknown exception | Ineligible | Fail closed with a stable category; avoid treating a possible policy denial or local defect as provider downtime. |
| Renderer, evaluator, artifact store, publisher, or downstream application failure after normalization | Ineligible | Reuse or recover the selected result; do not perform another model call. |

This initial policy covers provider downtime and confirmed availability failures. It deliberately distinguishes them from output quality and policy failures in the reviewable scope. The exact provider-code allowlist must come from the documentation analysis; this report does not invent undocumented Qwen/Grok codes.

## Durable attempt facts and usage

Introduce a closed `landing-provider-attempt/v1` record with:

- Tenant, repository, job, source input digest, pinned plan digest, ordinal, attempt ID, provider/profile/model/adapter/decoder identities, and request digest.
- State transitions such as `planned -> dispatching -> terminal`, with a terminal outcome/category and `dispatch_state = not_dispatched | dispatched | unknown`.
- Bounded start/end times and elapsed milliseconds; safe HTTP status/code when available; response digest when a complete bounded response was received.
- `usage_status = reported | unavailable | not_dispatched`. Reported input/output counts must both be valid integers; unavailable counts are null. `not_dispatched` explicitly establishes zero provider usage without pretending that an HTTP failure was free.
- Optional genuine v2 provider evidence when the existing adapter produced it. Do not fabricate successful evidence for an error or rewrite legacy zero counters as a factual observation.

Persist the intent and consume the slot before any external dispatch. Commit terminal facts before choosing Grok. Uniqueness by scoped job/plan/ordinal prevents concurrent submissions, new command keys, repeated reads, and restarts from buying additional attempts. A crash between intent persistence and send has unknown dispatch unless separately proven; absence of a receipt is not proof that no request occurred.

Parse and validate provider usage independently of draft success. A schema-invalid answer can still have genuine billable usage. Likewise, refusal or timeout does not imply zero. Known component counts are summed once across both attempts; a combined total is complete only when every dispatched attempt has reported usage. Otherwise report known totals as a lower bound plus `usage_complete=false` and the unknown attempt count. Do not hide failed-primary usage behind successful Grok evidence.

## Budgets and timeout semantics

The provable request budget is at most one dispatch per provider, two overall; no retries, hedge, speculative race, or fallback loop. Primary unavailability before dispatch does not itself create a billable call. Budget reservations for an ambiguous attempt stay consumed until resolved; they cannot be released as zero and spent again.

Keep each profile's existing response-byte, output, and timeout bounds. Pin the total coordinator deadline and each attempt deadline into the plan; a remaining-time calculation must not restart a fresh full chain on caller reconnect. The current 60-second per-profile default implies up to two provider windows if the approved total deadline allows them; it is not a guaranteed request duration once local build work is included. Configuration must make this explicit rather than inheriting a single-provider proxy timeout accidentally.

Grok's normalized output count includes reasoning, and its local cap is checked after consumption. It cannot prevent upstream spend beyond the visible generation cap. A two-attempt request ceiling and an observed-token acceptance ceiling therefore must not be described as a hard monetary budget. If financial reservations are required, use explicit reviewed per-provider prices/ceilings and an unknown-cost reservation; existing landing code has no such ledger today. Do not infer dollar costs or introduce the unrelated PostgreSQL execution-accounting subsystem solely to disguise this gap.

## Contract and identity recommendation

Add versioned `landing-failover-plan/v1` and `landing-normalization-selection/v1` contracts. The plan digest binds order, complete provider profile digests, capability intersection, eligibility policy, no-retry rule, deadlines, and attempt limits. The selection record binds ordered attempt digests, terminal selection, the actual winning provider evidence digest, and usage completeness. Bind it to the job and artifact result so provenance cannot be detached.

Preserve the existing provider-evidence v1/v2 schemas, domains, and historical bytes. Winning artifact evidence continues to say Qwen or Grok with its actual profile, and the service validates that profile against the pinned plan plus selection. Do not relax equality to an unbound membership test: ordinal, plan, input, winner, and evidence must agree. Do not silently change individual Qwen/Grok profile digests merely to identify the coordinator; give the coordinator its own policy identity. If lower-level decoder behavior changes, version only the affected provider adapter/decoder identities intentionally.

Use an additive, versioned SQLite migration for the attempt and selection journals, including validators and explicit old-schema handling. Existing jobs without attempt records remain historical, untracked records; do not synthesize an audit trail for them. Publish a new versioned status/evidence API for coordinator facts rather than changing the meaning of the closed public v1 response. Existing v1 consumers and retained-artifact readers must continue to work.

## Minimal implementation boundary

The smallest coherent unit is a normalization coordinator around provider attempts, before artifact generation. Reuse source validation and `decode_landing_draft`, the existing HTTP execution constraints, and the current renderer/evaluator/artifact path. Add typed attempt results at the transport/normalizer seam, a durable journal in the existing SQLite store, plan-aware service binding, and a versioned status/evidence surface.

An in-process wrapper can recover provider API failures but cannot recover the death of its own Qwen-host process. To satisfy primary-process-down behavior and preserve secret isolation, the coordinator must survive the primary worker and call separately isolated normalization workers over a closed local protocol. Workers own only their provider credential; the coordinator needs neither credential. Existing full landing submission services cannot be blindly raced or retried, because each can independently create artifacts while a response is lost. Either expose normalization-only worker operations or implement equivalent authoritative reconciliation of existing service jobs before selecting another full-service result; the integration architecture must make that choice explicit.

The coordinator owns one source lifetime and one final artifact path. Keep validated text/DOCX available until both permitted attempts terminate or the job stops, then purge through the existing tenant-scoped mechanism. Recovery that needs input after restart requires an explicitly retained, private source lifetime; the present purge/restart behavior cannot be assumed to provide it. No provider may turn source content into a new destination, profile, or fallback instruction.

## Required acceptance evidence

1. Qwen success sends no Grok request and retains original Qwen provenance.
2. Each eligible confirmed failure starts Grok exactly once; both failures terminate with both attempts represented.
3. Primary process/socket down before dispatch succeeds through Grok without obtaining the Qwen credential in the coordinator.
4. Lost response after submission performs read-only reconciliation; terminal primary success wins, unresolved ambiguity neither replays Qwen nor starts Grok.
5. Crash at intent/send/terminal/selection boundaries and concurrent/repeated submissions never exceed slot limits.
6. Refusal, moderation, local authorization, budget denial, unsafe input, wrong model, tool output, invalid usage, and downstream build failure never invoke Grok.
7. Factual usage survives rejected draft output; missing usage remains null/unknown; separate Grok reasoning is counted once; aggregate completeness remains false when primary usage is unknown.
8. Selected evidence, plan, attempts, source, job, and artifact must cross-bind; mutation of any identity is rejected.
9. Existing single-provider behavior, Qwen profiles, v1/v2 retained evidence, and old public API fixtures remain compatible.
10. Operator documentation distinguishes provider calls, local termination, unknown provider consumption, artifact completion, and later deployment authority.

## Decision for shared memory

Persist provider attempt facts before making the fallback decision, and separate availability failure from policy, integrity, and unknown-dispatch outcomes. This prevents a successful secondary response from erasing the primary's cost or turning a lost reply into an unbounded replay.
