## Что меняется в постановке задачи

Фабрика должна оптимизировать не количество сгенерированного кода и не число агентов, а путь от принятого поручения до принятого человеком результата. Эта редакция объединяет scope control, предметную приёмку, стоимость всех попыток, фактическое объяснение решений и отдельную среду Apple-разработки. ML/SHAP не становится обязательной зависимостью.

| Направление | Действие фабрики | Что не делать |
|---|---|---|
| Scope control | Выбирать micro/standard/high-risk по затронутым компонентам, сохранять phase/scope authority, ограничивать исследование. | Не повышать класс только из-за длинного сообщения или технологий вне изменения; не урезать критерии ради минимальности. |
| Доказательство результата | Разделять technical pass, semantic verdict и реальную человеческую приёмку; связывать их с точной ревизией. | Не объявлять задачу выполненной по одному зелёному тесту или созданному артефакту. |
| Повторы и очередь | Reconcile неопределённый исход, сохранять idempotency/fences, ограничивать непроверенную работу. | Не повторять оплачиваемый запрос при неизвестном эффекте; не генерировать быстрее, чем возможно проверить. |
| Время и деньги | Учитывать ожидание, исправления, все providers/attempts и стоимость с явной полнотой данных. | Не записывать unknown как 0 и не складывать параллельные интервалы как wall time. |
| Объяснения | Сначала фактический DecisionRecord: правило, наблюдение, evidence, ограничение, следующий шаг. | Не хранить скрытые рассуждения и не превращать объяснение в разрешение. |
| Objective-C/macOS | Linux координирует; зарегистрированный Mac/Xcode profile исполняет и независимо проверяет exact SHA. | Не подменять нативный результат Linux-тестом, x86_64 — arm64; не использовать GitHub Actions. |
| SHAP | После появления пригодной истории — одна observation-only модель и проверяемое объяснение прогноза. | Не подключать новый ML-стек заранее; не менять права, gate или M8 по прогнозу. |

## Очерёдность и независимо принимаемые результаты

**U0:** обновить представление о репозитории и открытых PR; проверить фактические швы реализации, совместимость контрактов и распределение требований по существующему коду. Не начинать с переписывания M4/M5/M6.

**U1:** scope/phase classification и bounded analysis. Уже выявленные точки проверки — `router.py::_domains`, `_risk`, `_complexity`: объединённые домены и длина текста сейчас влияют на процесс. Исправление обязано сохранить критические security/payment/production признаки и consumer instructions.

**U2:** фактические решения, время и стоимость. Затем **U3:** предметная приёмка, безопасные повторы и ограничение непроверенной работы. На U1 новую классификацию сначала сравнивать с действующей без изменения полномочий; применять после regression gates и появления U2-наблюдаемости.

**U4:** отдельный Apple profile и adapter. Исследование возможно параллельно; live qualification требует реального совместимого Mac и отдельного допуска оператора. Нет Mac — блокируется Apple-ветка, не полезная Linux-работа.

**U5:** условный ML/SHAP после U2 и пригодного dataset. Нет данных — `deferred/not_qualified`, без потери основного функционала.

**U6:** настоящий end-to-end Linux pilot; Apple pilot принимается отдельно после U4. **U7:** итоговые возможности, ограничения и recovery evidence. Восемь этапов — восемь границ приёмки, а не требование сделать гигантский PR. При необходимости этап дробится на меньшие согласованные change packages с сохранением traceability.

Меньше контекста при пропущенном инварианте означает провал приёмки. До этих gates новая подача остаётся observation-only.

Отдельно выполнить `git status --short` и `git diff --stat`, сохранить чужие изменения, обновить remote refs. Не считать исторические runtime/service/release SHA актуальным installed state.

Создать или разрешить действующий route штатным способом; не выдумывать `.grok-stack/runtime/active-route.json`, approvals или receipts. В U0 зафиксировать актуальные head/base, соответствие F01–F26 существующим модулям, совпадения с открытыми PR, начальный тестовый baseline и конкретные blockers. Не использовать ограничение анализа как повод пропустить проверку. Для application-code действует единственный write owner; независимые анализ и reviews допускаются параллельно в действующих квотах.

Для source merge обязателен актуальный App-owned `adaptive-trust-ci/verified@<policy-sha12>` и применимые внешние human-signed approvals. Имя наблюдённого baseline check — `adaptive-trust-ci/verified@06ecf1c875bc`; перед доставкой сверить действующую policy epoch.

Проверки PostgreSQL — только в отдельно созданной disposable DB, без чужих DSN. Build/test logs и `.xcresult` Mac-профиля должны происходить из реально выполненной независимой проверки, а не fixture. Исторические суммы, timestamps, runtime success и M8 acceptance не достраивать из предположений.

Не менять `main`, теги, immutable release ZIP, `VERSION`, deployed policy/holdout, signing keys, runtime credentials и продакшен в рамках документационного пакета. Сохранить текущие workstreams, в том числе PR #189 и #196; не закрывать их автоматически и не переносить сюда чужие change packages.

## Как отчитываться

На каждый этап предъявлять: F/AC coverage, применимые rule revisions и context digest, точные source/contract/profile identities, фактические команды и результаты, непроверенное, причину блокировки, residual risk, ссылки на evidence и отдельный статус external Trust CI. Наличие PR не означает запуск удалённого агента или установку обновления на Claw.

Итоговые статусы разделяются: `core_accepted`, `apple_accepted`, `ml_qualified`, `program_complete`, `m8_activated`. Для этого пакета они все **не установлены**. Регистрация ТЗ даёт **0 qualifying M8 tasks**, `authority_effect=none`; принятие исходников и работа одного provider не активируют M8. Программа может быть принята без необязательного ML, но обязательный Apple scope нельзя незаметно исключить.
