## 1. Зачем это обновление

Фабрика должна доводить ограниченную задачу до проверяемого результата: понять запрос → изучить относящийся к нему код → зафиксировать критерии → выбрать соразмерный процесс и исполнителя → сделать изменение → независимо проверить техническую и предметную правильность → ограниченно исправить ошибки → передать человеку результат и доказательства. Публикация, слияние и производственные действия остаются отдельными полномочиями.

Обновление соединяет пять обсуждений, а не создаёт пять новых подсистем. Приоритет: убрать лишнюю работу и неоднозначность статусов, доказать полный цикл, затем расширять среду исполнения и при необходимости добавлять прогнозную аналитику.

## 2. Что уже есть и чего нельзя объявлять готовым

Статически прочитаны `AGENTS.md`, `START_HERE.md`, профильные части `README.md`, `PROJECT_STATE.json`, `DARK_FACTORY_ROADMAP.md`, `factory/README.md`, `.grok-stack/adaptive_grok/router.py` и результаты поиска по шаблонам/installer.

| Область | Подтверждённое основание | Граница вывода |
|---|---|---|
| Маршрутизация | В router есть intent, risk, complexity, task_domains, роли и обязательные evidence. | Это не доказательство корректной классификации всех реальных задач. |
| Контроль и исполнение | В документации исходников описаны M4–M8, PostgreSQL, leases/fences, бюджеты, журнал, recovery; отдельно L5 использует SQLite. | Не переносить состояния или БД L5 в общий control plane молча. |
| Trust CI | Контракт закрепляет независимый App-owned exact-SHA check, внешнюю policy/holdout и человеческие security approvals. | Локальные тесты, запись в журнале или успешный Mac build не дают merge authority. |
| Runtime | Датированные записи содержат генерацию `artifact_ready` через Qwen/Grok. | Это исторические наблюдения, не проверка текущего Claw и не доказательство публикации или полного failover. |
| Полный цикл | В START_HERE остаётся unmet outcome: внешний пилот с maintainer acceptance. | Не выдавать наличие M0–M9 в коде за доказанную эксплуатационную автономность. |
| M8 | Roadmap требует минимум 30 принятых человеком задач одного exact-profile tuple; текущий предел полномочий — L2. | Регистрация проекта, synthetic tests и это ТЗ дают 0 qualifying tasks; активация не производится. |

Конкретная точка исправления в baseline: `_complexity` использует `len(text) < 300`, а высокий класс может следовать из `len(domains) >= 4`. `_domains` объединяет домены задачи с фоновыми доменами репозитория; `_risk` и набор анализаторов используют объединённый список. Поэтому подробное описание маленькой правки и полиглотность проекта могут увеличивать процесс. Удалять защитные признаки по одному только тексту задачи нельзя: требуется доказанная карта затронутых компонентов.

Открытые поставки, включая release-sync PR #189 и документационную регистрацию Mezo PR #196, не заменяются этим пакетом. `PROJECT_STATE.json` содержит датированные и исторические поля; его observed_main_sha не переписывается как будто это live status всех слоёв.

## 3. Архитектурное решение и границы

Использовать существующие слои: M1 — контракт задачи; локальный router — масштаб процесса; M4 — состояние, бюджет и аудит; M5 — изолированное исполнение; M6 — предметная валидация; M7 — пакет PR; M8 — доказательная оценка; M9 — отдельно разрешённая поставка. Новая управляющая система, новая общая очередь и новая БД не требуются.

Локальный route описывает рабочий процесс, но не выдаёт полномочий. Fact-based explanation и SHAP — разные типы артефактов. macOS — новый профиль исполнения/проверки, а не перенос координатора с Linux.

Не входят: автоматическое слияние, production deployment, изменение deployed Trust CI, доступ к ключам подписания, покупка Mac/облака, внедрение полного ML-platform, переписывание приложений клиентов, обязательные новые агенты, GitHub Actions. Bitrix core остаётся защищённым; расширения реализуются через `local/` по действующим правилам.

## 4. Требования

### F01. Единый контракт задачи и граница полномочий — S1, S2, S3

Контракт хранит objective, acceptance criteria с устойчивыми ID, фактическое состояние «сейчас», изменение «должно стать», инварианты, out-of-scope, предположения, затронутые компоненты, ожидаемые evidence, rollback и разрешённые фазы. Представление масштабируется по задаче, но обязательный результат не урезается.

Разделить намерение и действие: `analyze`, `specify`, `implement`, `verify`, `prepare_pr`, `publish`, `deploy`. Запрос «напиши ТЗ» разрешает подготовить запрошенные документы, но не менять приложение. Переход к реализации требует уже существующего явного поручения на реализацию либо нового согласования. Не задавать повторный вопрос, если поручение уже однозначно дано. Разрешение на код не означает разрешение на внешние операции.

### F02. Соразмерная классификация — S3

Сохранить совместимые значения `micro`, `standard`, `high-risk`, отдельно от `risk`. Вычислять класс из фактического изменения, контрактов, обратимости, неопределённости и затронутых зависимостей. Длина сообщения не повышает класс сама по себе. Фоновые технологии репозитория не включают профильных архитекторов без связи с изменением.

Различать `detected_repo_domains`, `task_domains`, `affected_domains` и подтверждающие пути. При неизвестном impact не объявлять micro автоматически: выполнить ограниченное уточнение; неизвестную критическую границу считать неразрешённой. Security, деньги, PII, внешние записи, destructive migrations и production сохраняют высокий риск независимо от числа строк. Появление нового риска требует пересчёта маршрута и объяснения.

### F03. Ограниченное исследование — S2, S3

До исследования зафиксировать `analysis_budget`: предельные раунды, provider usage, инструментальные операции и время по существующему механизму бюджета. Конкретные значения выбираются из версионированного профиля; это потолки, а не обязательная норма расхода. Начальные значения утверждаются на U1 по измеренному baseline, а не выдаются за исторически согласованные числа.

Исследование заканчивается, когда определены путь изменения, критерии и существенные риски. Новое чтение должно отвечать на конкретный нерешённый вопрос. По достижении лимита сохранить факты и blocker; продолжать независимые разрешённые задачи. Нельзя экономить путём пропуска финальной проверки, урезания функции или превращения неизвестного результата в успех.

### F04. Один владелец, управляемый контекст, отсутствие холостых циклов — S3

Один write owner на область изменения; независимые чтение и review можно распараллеливать в пределах текущих квот CPU/RAM/lease. Не считать число потоков CPU достаточным основанием загрузить все ядра. Анализаторы получают вопрос и ограниченный контекст, возвращают выводы со ссылками, не полные дубли транскриптов.

Сохранённый план и доказанные решения повторно используются до изменения их входов. No-op не запускает новый круг разработки/review. Для denied tool сохранить действующий circuit breaker: не повторять идентичное действие; после разрешённой смысловой переработки и повторного отказа блокировать зависимую цель, а не обходить запрет.

### F05. Предметная приёмка отдельно от технической — S1, S2

Технически зелёный результат не равен выполненной задаче. M6 проверяет каждый criterion ID независимыми данными/инвариантами и фиксирует `pass`, `fail`, `blocked` или `not_evaluated`. Критерий нельзя заменить более удобным для исполнителя. Проверяющий не редактирует candidate и не одобряет собственную реализацию.

Проверять реальные ограничения: единицы измерения и округление, разрешения, полноту выдачи, последствия повторов и сценарий пользователя. Тесты приложения, external holdout, предметная приёмка и решение человека отражаются отдельно. Спецификация/критерии и SHA должны быть привязаны к одному result bundle. Изменение кода, base или критериев инвалидирует относящийся к ним verdict.

### F06. Безопасные повторы и неопределённый исход — S1, S2

Сохранять существующую семантику idempotency, reconciliation, leases/fences и ограниченных retries. Отсутствие ответа не доказывает отсутствие эффекта. При `unknown` искать результат той же операции; не посылать её заново и не переключать provider, пока это может дублировать эффект/расход.

Ключ операции привязать к canonical project/task/action identity. Одинаковый ключ с иным payload отвергать. После готового артефакта генерацию не повторять; выдавать сохранённый результат. Retry разных попыток учитывается в стоимости одной задачи. Поздний ответ старого lease не может перезаписать новый результат.

### F07. Очередь непроверенной работы — S2, S3

Ввести/расширить конфигурируемый `max_unverified_inflight` на проект/профиль, не создавая вторую очередь. Считать зарезервированную генерацию и готовые, но не прошедшие требуемую проверку артефакты; брать слот атомарно до запуска. При достижении потолка останавливать новые генерации, но оставлять capacity на проверку, reconciliation и cleanup.

Человеческое ожидание показывать отдельной очередью `awaiting_human`, с отдельным лимитом при необходимости. После crash/cancel/restart счётчики восстанавливаются из durable state; нельзя освобождать слот только по таймеру, если эффект неизвестен. Проверить fairness между проектами и отсутствие дедлока при переполнении.

### F08. Измерение времени до приёмки — S1, S2

Основная метрика: `accepted_at - admitted_at`, где accepted_at создаётся по реальному решению уполномоченного человека о заданной ревизии. Для непринятой задачи выводить текущий возраст и состояние, не нулевое время и не фиктивную приёмку.

Разделять ожидание очереди, анализ, исполнение, проверку, исправления, внешние blockers и ожидание человека. Перекрывающиеся параллельные интервалы не складывать как wall time; отдельно измерять resource-time. Отмечать first-pass acceptance, число попыток, возвраты, человеческое время и дефекты после принятия. Неизвестное human time остаётся unknown. Определение окна наблюдения дефектов фиксируется в eval profile до сравнения.

### F09. Полная стоимость, включая неудачи — S2

Суммировать все попытки и всех providers, проверки, runners/infra и отдельно оценённый человеческий труд. Для каждой позиции фиксировать usage source, unit, currency, pricing version, actual/estimated/unknown. Неизвестная цена не равна нулю; полный cost выводится только при полном покрытии либо как явно маркированная неполная сумма.

Не смешивать валюты без сохранённого курса и даты. Не дублировать reasoning tokens, если provider уже включил их в output. Фактические затраты на отказавшие и брошенные задачи видны в cohort total; `cost_per_accepted_task` включает их при объявленной политике окна/кохорты. Нет принятых задач — показатель undefined, не 0. Прогноз не подменяет invoice.

### F10. Журнал фактических решений без ML — S4

Встроить `DecisionRecord` в существующую audit/evidence инфраструктуру. Запись содержит: schema_version, decision_id, project/task/run/attempt identity, observed_at, decision_kind, rule_id/version, входные факты или защищённые ссылки, outcome/reason_code, base/head SHA, spec/profile digest, evidence refs, ограничения и разрешённый следующий шаг. Это краткое обоснование по наблюдаемым фактам, не скрытая цепочка рассуждений LLM.

Примеры: почему выбран micro; почему остановлен retry; какой критерий не выполнен; почему нужен Mac; почему блокируется публикация. Запись не создаёт полномочий и не копирует закрытые trust secrets. Для нормативного решения использовать точное правило; для прогноза — тип `prediction`, не `policy_decision`.

### F11. Целостность журнала и читаемое объяснение — S4

Связать изменение состояния и событие решения атомарно, либо транзакционным outbox в пределах существующей БД. Повтор доставки не создаёт вторую запись. Исправление объяснения — новая запись с `supersedes`, а не переписывание истории. Ссылки и hashes проверяются; неизвестные факты маркируются явно.

Авторизованный пользователь видит «что произошло → на каком факте/правиле основано → чего не хватает → следующий разрешённый шаг». Нельзя придумывать объяснение после факта как будто оно было известно до решения. Экспортировать редактированное представление без секретов, prompts, customer payload и персональных данных. Cross-project доступ и высококардинальные metric labels запрещены.

### F12. Минимальный пилот прогнозирования — S4

Только после получения пригодной истории выбрать одну задачу: прогноз провала первой независимой технической проверки данного candidate. Время прогноза фиксируется до её начала. Product-test failure отличать от infrastructure abort, unavailable и pending; неизвестные labels не записывать как pass/fail. Повторные попытки одного change не расходятся по train/test.

Начать с простого baseline и одной небольшой модели. Использовать временное разбиение и проверку переносимости по проектам; исключить признаки, возникшие после предсказания. Сохранить dataset definition, split, model/feature schema versions, preprocessing, seed, метрики дискриминации и калибровки. Недостаточные данные означают `not_qualified`, а не обязательную установку библиотеки.

### F13. SHAP только для объяснения прогноза — S4

Артефакт содержит model digest, feature snapshot/schema, reference/background dataset digest, explainer/version/options, output space, expected value, prediction и полный вектор вкладов. Проверять аддитивность с объявленной tolerance в том же output space; log-odds нельзя подписывать как процентные пункты вероятности.

В интерфейсе можно показывать top factors, но полный вектор сохраняется. SHAP не доказывает причинность, качество кода, соблюдение закона или право merge/deploy. Сначала `observation_only`: прогноз не меняет разрешения, budget, route, required tests и M8. Ошибка SHAP не останавливает основной workflow; рекомендация становится unavailable. Любое последующее влияние модели — отдельное проверенное изменение.

### F14. macOS как отдельный capability profile — S5

Linux `claw` остаётся координатором. Профиль задаёт OS/architecture, Xcode build, SDK, project/workspace, scheme, deployment target, test plan, resource limits и доступные типы тестов. Значения извлекаются из проекта и capability probe, не выбираются через плавающий `latest`. Нужны полный Xcode, `xcodebuild` и XCTest для предусмотренного Apple pipeline; Linux-проверка переносимого кода не называется нативной macOS-приёмкой.

Поддержку `arm64`, `x86_64`, GUI и Metal объявлять раздельно. Успех на одной архитектуре не подтверждает другую; сборка универсального бинарника не доказывает запуск обеих частей. Профиль default-off. Покупка, аренда, установка и credentials требуют отдельного действия владельца.

### F15. Изоляция Mac и авторитет проверки — S1, S5

Использовать существующий M5 execution protocol с allowlisted Mac adapter, а не произвольный shell из текста запроса. Каждый job получает exact source identity, чистую рабочую область, отдельные DerivedData/temp/output, ограниченные сеть/секреты и lease/fence. Build scripts считаются недоверенным кодом.

Рабочая среда автора и независимый verifier разделены. Один физический Mac допустим только при доказанной границе изоляции/сброса; новая папка или другой Git worktree на скомпрометированном persistent host недостаточны. Verifier получает кандидат независимо и не доверяет принесённым исполнителем логам. Ключ App-owned Trust CI и ключ attestation не передаются build job. Доверие к новому Mac runner требует отдельно проверенной server-side регистрации.

### F16. Mac evidence, отказ и ресурсы — S5

Сохранить exit status процесса, bounded build/test logs, `.xcresult`, нормализованную сводку тестов, toolchain/SDK/OS/arch identity, exact SHA, время и artifact digests. Ноль выполненных обязательных тестов — не pass. Ошибка преобразователя отчёта не скрывает провал xcodebuild; неполный результат — incomplete/blocked. Подпись приложения, notarization и публикация — отдельные операции, не часть обычного тестового job.

При разрыве связи сохранять job identity и reconciliation, а не автоматически повторять сборку/эффекты. При нехватке памяти, диска или runner capability не перегружать Linux Trust CI; вернуть явный blocker. Исторически указано железо «Xeon 4xxx / 16 GB RAM / 480 GB storage», точная модель и свободные ресурсы не проверены. Прежний ориентир VM 8 GB / 4 vCPU / 120–150 GB — неподтверждённая оценка, не настройка по умолчанию.

Опорный вариант — доступный Mac либо допустимая macOS VM на Apple hardware. Обсуждавшийся Hackintosh сохраняется только как экспериментальный, неквалифицированный вариант: до установки отдельно проверить hardware, совместимость и применимую лицензию. Он не является обязательной зависимостью или источником официальной Apple/production квалификации.

### F17. Совместимость, поставляемые инструкции и наблюдаемость — S1, S3

Изменения контрактов версионировать. Существующие closed schemas и byte-pinned контракты нельзя молча расширять: выбирать совместимое additive расширение либо новый versioned endpoint/schema с сохранением старого reader. Исторические поля без данных остаются unknown; backfill не сочиняет timestamp, cost, approvals и predictions.

Синхронно обновлять инструкции фабрики, shipped adaptive-delivery skills и `.grok-stack/templates/consumer-AGENTS.md.tmpl`, затронутые consumer README/templates и installer tests. Обновление установленного consumer не должно затирать его собственные правила. Сохранить разделение factory PostgreSQL, Trust CI state и L5 SQLite. Не вводить общую transaction across these stores: использовать версионированные evidence links и idempotent import.

### F18. Доказательство полного цикла и M8 — S1–S5

Показать на реальной ограниченной задаче trace: intake → контракт → route → execution → technical checks → semantic verdict → при необходимости repair → ready-for-human/PR → человеческое решение. Хранить exact SHA, profiles, все попытки/затраты, внешние checks и остаточные ограничения. Runtime generation, draft PR, human acceptance и deployment — разные результаты.

Сначала принять Linux core; Apple track и ML track имеют собственные статусы. Отсутствие Mac блокирует только Apple-dependent задачи, отсутствие обучаемой модели не блокирует основной цикл. Общая программа не считается полностью выполненной, пока обязательный Apple scope не прошёл приёмку либо не исключён владельцем явно; ML остаётся условным.

M8 считать только по действующим exact-profile правилам и минимуму 30 принятых человеком задач, без смешения репозиториев/профилей и без автоматической активации. Смена значимых model/prompt/policy/runner/holdout составляющих создаёт новую применимую когорту. Это обновление само по себе не добавляет принятых задач и не повышает автономность.

## 5. Общие инварианты

Любой положительный вывод связан с конкретными SHA, criterion и profile. Никакой agent-produced artifact не создаёт Trust CI authority. Нет live effects без действующего точного разрешения; security approvals подписывает человек вне agent environment. Нет новых GitHub Actions. Нет чтения `.env`/private keys агентом, поддельных tests/receipts/checks, изменения immutable release artifacts, скрытой повторной оплаты provider и потери существующих изменений.

Журнал не хранит скрытые reasoning streams. Квоты не обходятся дополнительными агентами. Rollback не удаляет исторические evidence и реальные побочные эффекты. Улучшение скорости не достигается снижением полноты функции, отключением проверок или исключением неудачных попыток из отчёта.

**Предлагаемые новые узкие модули:** `.grok-stack/adaptive_grok/scope_control.py`; `factory/src/adaptive_factory/decision_records.py`, `delivery_metrics.py`, `macos_executor.py`; отдельный optional prediction/explanation module. Это проектные имена, не утверждение, что такие файлы уже существуют. В U0 проверить ownership и актуальную архитектуру; существующий подходящий модуль расширить вместо дубля, решение записать в child change.

## 9. Проверки и Definition of Done

Перед каждой реализацией на Claw: отдельно `git status --short`, `git diff --stat`, затем fetch и чтение entrypoint/state/AGENTS. Существующие изменения сохранить; local route и grants не выдумывать. Проверить актуальные имена тестов/профиль, зависимости и disposable DB before execution.

Для изменённого product tree выполнить `python3 scripts/grok_verify.py --mode pr`, выбранные независимые review и финальную проверку дерева с сохранёнными reports. Factory PostgreSQL tests запускаются только в новой disposable PostgreSQL 17 DB; не читать production `.env` и не использовать Trust CI DSN. Mac build/tests выполняются в зарегистрированном профиле с сохранением exit status и `.xcresult`. Эти команды — требования будущей реализации, не результаты выполнения в этом пакете.

**Core accepted:** U1–U3 и Linux U6 приняты; все применимые AC проходят; существующие проверки не ослаблены; реальные время/стоимость/предметная приёмка наблюдаемы. **Apple accepted:** дополнительно U4, Apple U6, AC38 и независимая проверка границы runner. **ML qualified:** только при выполненных U5 gates; может оставаться deferred без провала core. **Program complete:** core и обязательный Apple scope приняты либо его исключение явно записано владельцем; U7 оформлен; каждый deferred пункт видим.

Документ, открытый PR, successful local tests, accepted pilot и активированная M8 — разные статусы. Для принятия source PR нужен текущий App-owned `adaptive-trust-ci/verified@<policy-sha12>` на exact head и применимые человеческие подписи. Публикация и production требуют своих полномочий.

## 10. Включение и откат

Вводить изменения поэтапно: сначала измерение/объяснения, затем сравнение нового routing в observation mode, после regression gates — применение scope control. Обязательные safety gates не отключаются флагом эксперимента. Mac и SHAP default-off до своих qualification gates.

При ошибке scope вернуть предыдущий рабочий профиль без удаления истории; остановить новые затронутые dispatch, сохранить и reconcile inflight jobs. При проблеме Mac запретить новые Apple jobs, завершить/отменить по lease и сохранить отчёты. При ошибке ML отключить прогнозы, не основной pipeline. Миграции только additive/forward recovery с проверкой старых readers: rollback кода не означает безопасный down-migration или удаление evidence.
