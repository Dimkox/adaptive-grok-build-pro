## 1. Зачем это обновление

Фабрика должна доводить ограниченную задачу до проверяемого результата: понять запрос → изучить относящийся к нему код → зафиксировать критерии → выбрать соразмерный процесс и исполнителя → сделать изменение → независимо проверить техническую и предметную правильность → ограниченно исправить ошибки → передать человеку результат и доказательства. Публикация, слияние и производственные действия остаются отдельными полномочиями.

Обновление соединяет пять исходных обсуждений и предоставленные владельцем дополнения S6 о контексте и S7 о границах данных и проверке поведения, не создавая новые управляющие подсистемы. Приоритет: убрать лишнюю работу и неоднозначность статусов, доказать полный цикл, затем расширять среду исполнения и при необходимости добавлять прогнозную аналитику.

Конкретная точка исправления в baseline: `_complexity` использует `len(text) < 300`, а высокий класс может следовать из `len(domains) >= 4`. `_domains` объединяет домены задачи с фоновыми доменами репозитория; `_risk` и набор анализаторов используют объединённый список. Поэтому подробное описание маленькой правки и полиглотность проекта могут увеличивать процесс. Удалять защитные признаки по одному только тексту задачи нельзя: требуется доказанная карта затронутых компонентов.

Открытые поставки, включая release-sync PR #189 и документационную регистрацию Mezo PR #196, не заменяются этим пакетом. `PROJECT_STATE.json` содержит датированные и исторические поля; его observed_main_sha не переписывается как будто это live status всех слоёв.

**Уточнение baseline для S7.** Прочитанный PostToolUse hook инвалидирует receipts при изменении дерева; проверки содержимого tool result в этом файле нет. В `brokers.py` видны типизированные proposals, лимиты и очистка известных секретных форматов; это не доказательство перехвата каждого ответа до следующего model request. `shadow_evaluation.py` агрегирует исходы когорты; наличие этого агрегатора не доказывает действующий механизм парного допуска обновлений. Новые требования закрывают именно эти проверяемые границы, а не заменяют существующие компоненты.

Текущий `AGENTS.md` также требует измерять доступную вычислительную ёмкость до локального планирования и использовать fail-closed выбор области проверки через `grok_verify --mode pr` (issue #205 / PR #207). Его `docs-state-focused` — уже существующий выбор тестов исходников, а не новый behavior gate F26. Ни маршрут, ни классификатор F26 не получают права самовольно пропускать обязательные проверки. Указанные выше состояния прежних PR/релизов — датированный контекст v1.0, не новая проверка каждого из них.

## 3. Архитектурное решение и границы

Использовать существующие слои: M1 — контракт задачи; локальный router — масштаб процесса; M4 — состояние, бюджет и аудит; M5 — изолированное исполнение; M6 — предметная валидация; M7 — пакет PR; M8 — доказательная оценка; M9 — отдельно разрешённая поставка. Новая управляющая система, новая общая очередь и новая БД не требуются.

Локальный route описывает рабочий процесс, но не выдаёт полномочий. Fact-based explanation и SHAP — разные типы артефактов. macOS — новый профиль исполнения/проверки, а не перенос координатора с Linux.

Не входят: автоматическое слияние, production deployment, изменение deployed Trust CI, доступ к ключам подписания, покупка Mac/облака, внедрение полного ML-platform, переписывание приложений клиентов, обязательные новые агенты, GitHub Actions. Bitrix core остаётся защищённым; расширения реализуются через `local/` по действующим правилам.

## 4. Требования

### F01. Единый контракт задачи и граница полномочий — S1, S2, S3

Контракт хранит objective, acceptance criteria с устойчивыми ID, фактическое состояние «сейчас», изменение «должно стать», инварианты, out-of-scope, предположения, затронутые компоненты, ожидаемые evidence, rollback и разрешённые фазы. Представление масштабируется по задаче, но обязательный результат не урезается.

Разделить намерение и действие: `analyze`, `specify`, `implement`, `verify`, `prepare_pr`, `publish`, `deploy`. Запрос «напиши ТЗ» разрешает подготовить запрошенные документы, но не менять приложение. Переход к реализации требует уже существующего явного поручения на реализацию либо нового согласования. Не задавать повторный вопрос, если поручение уже однозначно дано. Разрешение на код не означает разрешение на внешние операции.

### F02. Соразмерная классификация — S3

Сохранить совместимые значения `micro`, `standard`, `high-risk`, отдельно от `risk`. Вычислять класс из фактического изменения, контрактов, обратимости, неопределённости и затронутых зависимостей. Длина сообщения не повышает класс сама по себе. Фоновые технологии репозитория не включают профильных архитекторов без связи с изменением.

Различать `detected_repo_domains`, `task_domains`, `affected_domains` и подтверждающие пути. При неизвестном impact не объявлять micro автоматически: выполнить ограниченное уточнение; неизвестную критическую границу считать неразрешённой. Security, деньги, PII, внешние записи, destructive migrations и production сохраняют высокий риск независимо от числа строк. Появление нового риска требует пересчёта маршрута и объяснения.

### F03. Ограниченное исследование — S2, S3

До исследования зафиксировать `analysis_budget`: предельные раунды, provider usage, инструментальные операции и время по существующему механизму бюджета. Конкретные значения выбираются из версионированного профиля; это потолки, а не обязательная норма расхода. Начальные значения утверждаются на U1 по измеренному baseline, а не выдаются за исторически согласованные числа.

Исследование заканчивается, когда определены путь изменения, критерии и существенные риски. Новое чтение должно отвечать на конкретный нерешённый вопрос. По достижении лимита сохранить факты и blocker; продолжать независимые разрешённые задачи. Нельзя экономить путём пропуска финальной проверки, урезания функции или превращения неизвестного результата в успех.

### F04. Один владелец, управляемый контекст, отсутствие холостых циклов — S3

Один write owner на область изменения; независимые чтение и review можно распараллеливать в пределах текущих квот CPU/RAM/lease. Не считать число потоков CPU достаточным основанием загрузить все ядра. Анализаторы получают вопрос и ограниченный контекст, возвращают выводы со ссылками, не полные дубли транскриптов.

Сохранённый план и доказанные решения повторно используются до изменения их входов. No-op не запускает новый круг разработки/review. Для denied tool сохранить действующий circuit breaker: не повторять идентичное действие; после разрешённой смысловой переработки и повторного отказа блокировать зависимую цель, а не обходить запрет.

### F05. Предметная приёмка отдельно от технической — S1, S2

Технически зелёный результат не равен выполненной задаче. M6 проверяет каждый criterion ID независимыми данными/инвариантами и фиксирует `pass`, `fail`, `blocked` или `not_evaluated`. Критерий нельзя заменить более удобным для исполнителя. Проверяющий не редактирует candidate и не одобряет собственную реализацию.

Проверять реальные ограничения: единицы измерения и округление, разрешения, полноту выдачи, последствия повторов и сценарий пользователя. Тесты приложения, external holdout, предметная приёмка и решение человека отражаются отдельно. Спецификация/критерии и SHA должны быть привязаны к одному result bundle. Изменение кода, base или критериев инвалидирует относящийся к ним verdict.

Уточнение S7: review report разделяет доказанные критерии, missing/inconclusive evidence и проверки, подтверждающие лишь наличие текста вместо требуемого свойства. Для критичных критериев обязателен ограниченный отрицательный контроль по F22: нарушение защищаемого условия должно обнаруживаться проверкой. Независимый reviewer оценивает архитектуру, безопасность, предметный смысл и пробелы evidence; форматтер и успешный запуск тестов не заменяют это решение.

### F06. Безопасные повторы и неопределённый исход — S1, S2

Сохранять существующую семантику idempotency, reconciliation, leases/fences и ограниченных retries. Отсутствие ответа не доказывает отсутствие эффекта. При `unknown` искать результат той же операции; не посылать её заново и не переключать provider, пока это может дублировать эффект/расход.

Ключ операции привязать к canonical project/task/action identity. Одинаковый ключ с иным payload отвергать. После готового артефакта генерацию не повторять; выдавать сохранённый результат. Retry разных попыток учитывается в стоимости одной задачи. Поздний ответ старого lease не может перезаписать новый результат.

Уточнение S7: контракт внешнего адаптера различает приём запроса получателем и подтверждённый требуемый эффект. До dispatch определяются effect identity, наблюдаемый postcondition, источник подтверждения, ограниченный срок наблюдения и следующие разрешённые действия. HTTP 2xx/202 либо подтверждение транспорта не означают успешную бизнес-операцию сами по себе. Для публикации сверяются нужный artifact digest и целевой адрес/идентичность, для PR — нужный repository/branch/head; если требуемый postcondition действительно состоит лишь в приёме, это явно записывается в контракте и не называется выполнением более позднего эффекта. При потере подтверждения после эффекта сохранять ту же operation identity и выполнять observation/reconciliation без повторной записи; отказ после приёма отражать как failure, истечение срока наблюдения — как unknown/blocked, не success. Поздний результат проверяется по fence и identity.

### F07. Очередь непроверенной работы — S2, S3

Ввести/расширить конфигурируемый `max_unverified_inflight` на проект/профиль, не создавая вторую очередь. Считать зарезервированную генерацию и готовые, но не прошедшие требуемую проверку артефакты; брать слот атомарно до запуска. При достижении потолка останавливать новые генерации, но оставлять capacity на проверку, reconciliation и cleanup.

Человеческое ожидание показывать отдельной очередью `awaiting_human`, с отдельным лимитом при необходимости. После crash/cancel/restart счётчики восстанавливаются из durable state; нельзя освобождать слот только по таймеру, если эффект неизвестен. Проверить fairness между проектами и отсутствие дедлока при переполнении.

### F08. Измерение времени до приёмки — S1, S2

Основная метрика: `accepted_at - admitted_at`, где accepted_at создаётся по реальному решению уполномоченного человека о заданной ревизии. Для непринятой задачи выводить текущий возраст и состояние, не нулевое время и не фиктивную приёмку.

Разделять ожидание очереди, анализ, исполнение, проверку, исправления, внешние blockers и ожидание человека. Перекрывающиеся параллельные интервалы не складывать как wall time; отдельно измерять resource-time. Отмечать first-pass acceptance, число попыток, возвраты, человеческое время и дефекты после принятия. Неизвестное human time остаётся unknown. Определение окна наблюдения дефектов фиксируется в eval profile до сравнения.

### F09. Полная стоимость, включая неудачи — S2

Суммировать все попытки и всех providers, проверки, runners/infra и отдельно оценённый человеческий труд. Для каждой позиции фиксировать usage source, unit, currency, pricing version, actual/estimated/unknown. Неизвестная цена не равна нулю; полный cost выводится только при полном покрытии либо как явно маркированная неполная сумма.

Не смешивать валюты без сохранённого курса и даты. Не дублировать reasoning tokens, если provider уже включил их в output. Фактические затраты на отказавшие и брошенные задачи видны в cohort total; `cost_per_accepted_task` включает их при объявленной политике окна/кохорты. Нет принятых задач — показатель undefined, не 0. Прогноз не подменяет invoice.

### F10. Журнал фактических решений без ML — S4

Встроить `DecisionRecord` в существующую audit/evidence инфраструктуру. Запись содержит: schema_version, decision_id, project/task/run/attempt identity, observed_at, decision_kind, rule_id/version, входные факты или защищённые ссылки, outcome/reason_code, base/head SHA, spec/profile digest, evidence refs, ограничения и разрешённый следующий шаг. Это краткое обоснование по наблюдаемым фактам, не скрытая цепочка рассуждений LLM.

Примеры: почему выбран micro; почему остановлен retry; какой критерий не выполнен; почему нужен Mac; почему блокируется публикация. Запись не создаёт полномочий и не копирует закрытые trust secrets. Для нормативного решения использовать точное правило; для прогноза — тип `prediction`, не `policy_decision`.

### F11. Целостность журнала и читаемое объяснение — S4

Связать изменение состояния и событие решения атомарно, либо транзакционным outbox в пределах существующей БД. Повтор доставки не создаёт вторую запись. Исправление объяснения — новая запись с `supersedes`, а не переписывание истории. Ссылки и hashes проверяются; неизвестные факты маркируются явно.

Авторизованный пользователь видит «что произошло → на каком факте/правиле основано → чего не хватает → следующий разрешённый шаг». Нельзя придумывать объяснение после факта как будто оно было известно до решения. Экспортировать редактированное представление без секретов, prompts, customer payload и персональных данных. Cross-project доступ и высококардинальные metric labels запрещены.

Уточнение S7: события transport accepted, effect observed, rejected и observation unavailable должны различаться в журнале. Связь намерения, отправки и наблюдения содержит operation ID, postcondition и evidence ref. Использовать уже существующие outbox/reconciliation там, где они есть; локальная атомарная запись не доказывает атомарность удалённого действия. Новые слова для событий в этом ТЗ не разрешают добавлять значения в закрытый wire contract без версионирования.

### F12. Минимальный пилот прогнозирования — S4

Только после получения пригодной истории выбрать одну задачу: прогноз провала первой независимой технической проверки данного candidate. Время прогноза фиксируется до её начала. Product-test failure отличать от infrastructure abort, unavailable и pending; неизвестные labels не записывать как pass/fail. Повторные попытки одного change не расходятся по train/test.

Начать с простого baseline и одной небольшой модели. Использовать временное разбиение и проверку переносимости по проектам; исключить признаки, возникшие после предсказания. Сохранить dataset definition, split, model/feature schema versions, preprocessing, seed, метрики дискриминации и калибровки. Недостаточные данные означают `not_qualified`, а не обязательную установку библиотеки.

### F13. SHAP только для объяснения прогноза — S4

Артефакт содержит model digest, feature snapshot/schema, reference/background dataset digest, explainer/version/options, output space, expected value, prediction и полный вектор вкладов. Проверять аддитивность с объявленной tolerance в том же output space; log-odds нельзя подписывать как процентные пункты вероятности.

В интерфейсе можно показывать top factors, но полный вектор сохраняется. SHAP не доказывает причинность, качество кода, соблюдение закона или право merge/deploy. Сначала `observation_only`: прогноз не меняет разрешения, budget, route, required tests и M8. Ошибка SHAP не останавливает основной workflow; рекомендация становится unavailable. Любое последующее влияние модели — отдельное проверенное изменение.

### F14. macOS как отдельный capability profile — S5

Linux `claw` остаётся координатором. Профиль задаёт OS/architecture, Xcode build, SDK, project/workspace, scheme, deployment target, test plan, resource limits и доступные типы тестов. Значения извлекаются из проекта и capability probe, не выбираются через плавающий `latest`. Нужны полный Xcode, `xcodebuild` и XCTest для предусмотренного Apple pipeline; Linux-проверка переносимого кода не называется нативной macOS-приёмкой.

Поддержку `arm64`, `x86_64`, GUI и Metal объявлять раздельно. Успех на одной архитектуре не подтверждает другую; сборка универсального бинарника не доказывает запуск обеих частей. Профиль default-off. Покупка, аренда, установка и credentials требуют отдельного действия владельца.

### F15. Изоляция Mac и авторитет проверки — S1, S5

Использовать существующий M5 execution protocol с allowlisted Mac adapter, а не произвольный shell из текста запроса. Каждый job получает exact source identity, чистую рабочую область, отдельные DerivedData/temp/output, ограниченные сеть/секреты и lease/fence. Build scripts считаются недоверенным кодом.

Рабочая среда автора и независимый verifier разделены. Один физический Mac допустим только при доказанной границе изоляции/сброса; новая папка или другой Git worktree на скомпрометированном persistent host недостаточны. Verifier получает кандидат независимо и не доверяет принесённым исполнителем логам. Ключ App-owned Trust CI и ключ attestation не передаются build job. Доверие к новому Mac runner требует отдельно проверенной server-side регистрации.

### F16. Mac evidence, отказ и ресурсы — S5

Сохранить exit status процесса, bounded build/test logs, `.xcresult`, нормализованную сводку тестов, toolchain/SDK/OS/arch identity, exact SHA, время и artifact digests. Ноль выполненных обязательных тестов — не pass. Ошибка преобразователя отчёта не скрывает провал xcodebuild; неполный результат — incomplete/blocked. Подпись приложения, notarization и публикация — отдельные операции, не часть обычного тестового job.

При разрыве связи сохранять job identity и reconciliation, а не автоматически повторять сборку/эффекты. При нехватке памяти, диска или runner capability не перегружать Linux Trust CI; вернуть явный blocker. Исторически указано железо «Xeon 4xxx / 16 GB RAM / 480 GB storage», точная модель и свободные ресурсы не проверены. Прежний ориентир VM 8 GB / 4 vCPU / 120–150 GB — неподтверждённая оценка, не настройка по умолчанию.

Опорный вариант — доступный Mac либо допустимая macOS VM на Apple hardware. Обсуждавшийся Hackintosh сохраняется только как экспериментальный, неквалифицированный вариант: до установки отдельно проверить hardware, совместимость и применимую лицензию. Он не является обязательной зависимостью или источником официальной Apple/production квалификации.

### F17. Совместимость, поставляемые инструкции и наблюдаемость — S1, S3

Изменения контрактов версионировать. Существующие closed schemas и byte-pinned контракты нельзя молча расширять: выбирать совместимое additive расширение либо новый versioned endpoint/schema с сохранением старого reader. Исторические поля без данных остаются unknown; backfill не сочиняет timestamp, cost, approvals и predictions.

Синхронно обновлять инструкции фабрики, shipped adaptive-delivery skills и `.grok-stack/templates/consumer-AGENTS.md.tmpl`, затронутые consumer README/templates и installer tests. Обновление установленного consumer не должно затирать его собственные правила. Сохранить разделение factory PostgreSQL, Trust CI state и L5 SQLite. Не вводить общую transaction across these stores: использовать версионированные evidence links и idempotent import.

Уточнение S7: для каждого применимого внешнего адаптера составить карту postcondition → observer → существующие tests; новый тест добавлять лишь при пробеле. Не вводить Kafka, общую шину, новую БД/очередь или распределённый координатор транзакций. Обмен командами и подтверждениями не объявлять общей транзакцией между хранилищами. Новые поля tool-result/eval evidence вводить через действующие версионированные пакеты с обратным чтением; старые unknown не превращать в измеренный ноль.

### F18. Доказательство полного цикла и M8 — S1–S5

Показать на реальной ограниченной задаче trace: intake → контракт → route → execution → technical checks → semantic verdict → при необходимости repair → ready-for-human/PR → человеческое решение. Хранить exact SHA, profiles, все попытки/затраты, внешние checks и остаточные ограничения. Runtime generation, draft PR, human acceptance и deployment — разные результаты.

Сначала принять Linux core; Apple track и ML track имеют собственные статусы. Отсутствие Mac блокирует только Apple-dependent задачи, отсутствие обучаемой модели не блокирует основной цикл. Общая программа не считается полностью выполненной, пока обязательный Apple scope не прошёл приёмку либо не исключён владельцем явно; ML остаётся условным.

M8 считать только по действующим exact-profile правилам и минимуму 30 принятых человеком задач, без смешения репозиториев/профилей и без автоматической активации. Смена значимых model/prompt/policy/runner/holdout составляющих создаёт новую применимую когорту. Это обновление само по себе не добавляет принятых задач и не повышает автономность.

### F19. Прицельный вход в проект внутри существующего route — S6

Разделить контекст на обязательную часть и раскрываемые по задаче материалы. Порядок: действующие обязательные инструкции фабрики и подключённого проекта → краткая карта проекта и словарь терминов → правила и публичные контракты затронутой области → текущий change-spec → нужные исходники и проверки. Краткая карта содержит точки входа, границы компонентов и ссылки, а не пересказ реализации.

Выбор материалов опирается на `affected_domains`/пути из F02 и проверенные зависимости, включая общие контракты и пограничные инварианты. Один поиск по словам задачи недостаточен. Для включения материала сохраняется причина; при обнаружении новой зависимости контекст расширяется ограниченно и наблюдаемо. История релизов фабрики не входит по умолчанию в задачу отображения кривой внешнего проекта, если не установлена её применимость.

Нельзя молча сокращать обязательные инструкции, пропускать вложенные правила затронутых путей или отрезать инварианты из-за лимита токенов. Пока новая навигация не принята и entrypoint-инструкции не обновлены штатно, существующий обязательный bootstrap остаётся действующим. Недоступная обязательная ссылка либо переполнение обязательной части означает конкретный blocker зависимой работы; отсутствующий необязательный индекс допускает ограниченный поиск существующих первоисточников. Никаких новых сервисов, контекстных агентов или отдельной очереди.

### F20. Переиспользование утверждённых правил подключённого проекта — S6

Постоянные предметные правила принадлежат целевому проекту, а не фабрике и не каждому отдельному чату. Использовать существующий target-owned governance/contract источник; для правила сохранять repository identity, устойчивый rule ID, revision, scope, statement, статус, provenance и имеющиеся review/approval evidence. Совпадающий rule ID в другом репозитории — другая сущность. Кандидаты из кода, документации или вывода модели не становятся действующими автоматически.

Сохранить штатный lifecycle M3 (`candidate`, `reviewed`, `approved`, `active`, `deprecated`, `revoked`) и его правила применения. Запись `approved` сама по себе не доказывает состоявшуюся активацию; агент не заполняет человеческий approval от своего имени. Не создавать второй реестр в `agent-context/`. Навигация и словарь ссылаются на один первоисточник, а проверяемая выдержка не переопределяет его. Конфликт предметных источников разрешается по действующим полномочиям и с фиксацией решения, не выбором более удобной формулировки.

Для Pump Selector включить четыре предметных regression fixtures: кривая/схема/паспорт принадлежат одной модели и исполнению; отсутствующее значение не подменяется нулём; единицы сохраняются либо преобразуются явно; 256 точек проверяются отдельно от происхождения и точности кривой. Это требования к будущим проверкам и примеры проектных правил, не утверждение о текущем поведении Pump Selector и не разрешение менять его репозиторий этим PR.

### F21. Воспроизводимый снимок контекста — S6

Внутри текущего change package предусмотреть `context-manifest.json`: версионированный манифест происхождения и выбора материалов, не новую нормативную спецификацию. Он связывает целевой репозиторий, source/base snapshot, route/change ID, `change_spec_digest`, версии сборщика/схемы, обязательные инструкции, использованные rules/contracts, навигацию, проверяемые выдержки и причины включения. Для каждого источника нужны точный ref/blob или content digest и локатор. Для незакоммиченного candidate нужен воспроизводимый snapshot/fingerprint, одного HEAD недостаточно.

`context_digest` вычисляется по канонической семантической части: поле самого digest и переменные timestamp/метрики исключаются; pins, selections, mappings и содержимое выдержек входят. Не создавать циклическую зависимость digest спецификации и манифеста. Полная связь с execution/validation evidence выполняется существующим пакетом результата либо явно версионированным расширением контракта. Нельзя дописать неподдерживаемое поле в closed packet/schema и назвать совместимым изменением.

Исполнитель и проверяющий используют один набор нормативных pins; проверяющий вправе независимо расширить read-only исследование. Изменение применимого правила, контракта, обязательной инструкции или области изменения делает прежний контекст stale: affected task переоценивается, новая ревизия сохраняется отдельно. Смена candidate SHA отдельно инвалидирует прежние результаты по F05/F17. Изменение несвязанного архивного пакета не подменяет применимые pins; это не отменяет exact-SHA проверки нового candidate. Источники должны быть доступны для воспроизведения: hash отсутствующего файла сам по себе недостаточен.

### F22. Связь проектного правила с типизированным критерием и исполненной проверкой — S6

Использовать существующие `invariants`, `forbidden_outcomes`, `contracts`, `acceptance_criteria` и `criterion_coverage()`, не создавать второй evaluator. В `change-spec.yaml` остаётся полная согласованная формулировка критерия/инварианта со штатным ID и evidence selector. Манифест связывает этот ID с repository/rule/revision/source digest. Это замороженная проекция первоисточника, не независимая копия правила, которую можно редактировать отдельно.

На проверенном source `5713b407818dbb6c2d1acfcb0b0d9661c32e1153` схема change-spec v2 закрыта (`additionalProperties=false`). Поэтому не добавлять туда `rule_refs` или `context_digest` без отдельной версионированной миграции. Начальная интеграция сохраняет v2 и использует sidecar mapping. Новые поля sidecar — проектируемый контракт, не уже поддерживаемый runtime API. Проекция должна сохранять смысл и все условия действующего правила; расхождение блокирует приёмку до исправления/разрешённого пересогласования.

Различать `mapped` и фактически выполненную проверку. К evidence исполнения привязывать criterion/rule identity, candidate SHA, context digest, команду/селектор, результат и digest отчёта. Для перенесённого критерия без подходящего теста сохранять missing evidence, а не «документация обновлена = pass». Проверки отрицательных случаев обязательны: схема модели B в карточке A; правильные 256 точек чужой кривой; unknown, превращённый в ноль; неверное преобразование единиц. Зелёный общий тест карточки не закрывает эти условия автоматически.

Уточнение S7: отрицательный контроль критичного критерия выполняется reviewer в изолированной временной копии точного candidate, не в проверяемом worktree. Фиксируются правило/criterion, идентичность исходного snapshot, внесённое нарушение, команда, результат «исходный проходит → нарушенный не проходит → восстановленный проходит» и fingerprint candidate до/после. Failure должен относиться к проверяемому свойству, а не только к синтаксической ошибке или недоступной зависимости. Survived mutant — finding; неисполненный/неубедительный probe — inconclusive, не pass. Переиспользовать действующие mutation-probe правила reviewer; не вводить бессмысленный общий процент mutation score и не позволять implementer самому утвердить собственное evidence.

### F23. Активная навигация, архив и граница доверия — S6

После завершения change исключать его пакет из чтения по умолчанию, сохраняя исходное содержимое, идентификаторы, pins, результаты и доступ по точной ссылке. Архивирование может быть изменением индекса/статуса: физический перенос или удаление файлов не требуется. Не ломать старые ссылки и digest bindings. Постоянные правила остаются доступны через действующий реестр; разовое решение не становится постоянным без штатного review/approval.

Карту/словарь/правило обновлять при изменении смысла, публичного контракта, инварианта, границы компонента или точки навигации. Косметическая правка исходника не должна автоматически порождать переписанную документацию. Сгенерированный обзор всегда помечается производным; Markdown и текст репозитория не могут выдать production/merge/secret authority. Подмешанная команда из документа, тестовой фикстуры или истории не становится инструкцией управляющему слою.

При нехватке надёжной навигации возвращаться к существующим авторитетным источникам в пределах F03, а не к стороннему хранилищу по умолчанию. OpenViking, vector database, новая система памяти и энциклопедическая генерация документации не входят в scope этой доработки.

### F24. Измерение пользы без потери предметной правильности — S6

До эксперимента зафиксировать одни и те же задачи и snapshots, версии моделей/prompts/tools, бюджеты и критерии для старой и новой подачи контекста. Минимальный проектный набор — 12 сценариев: 4 Pump Selector с условиями F20, 4 задачи самой фабрики, 4 задачи с межкомпонентными зависимостями/конфликтами правил. Это заданный размер приёмочного набора, не число уже выполненных задач и не статистическое доказательство для всех проектов.

Учитывать контекст всех анализаторов, исполнителя, проверяющих и повторных попыток: unique bytes, суммарные прочитанные bytes, число повторных чтений, input/cached tokens по фактическому usage, затраты подготовки/обновления контекста, время, число исправлений из-за неверно понятого требования и итоговую criterion coverage. Размер файла не равен токенам; неизвестный tokenizer/provider usage остаётся unknown, proxy по bytes подписывается отдельно. Нельзя убрать расход на сборку контекста из сравнения или сравнивать прогретый новый cache с холодным старым без раздельного отчёта.

Приёмка оптимизации: все обязательные положительные/отрицательные проверки пройдены, нет новых пропущенных инвариантов/неразрешённых действий, а на заранее выбранных случаях с нерелевантной историей доказано строгое снижение загрузки контекста и повторных чтений. По всему набору показать p50/p95, расходы и регрессии; при ухудшении качества оптимизацию не включать. Стохастические показатели маркировать как пилотные, не обещать гарантированный процент экономии. Сначала observation-only сбор/сравнение; включение после U2-наблюдаемости и U6-приёмки. Это не квалификация M8.

### F25. Проверяемая граница «ответ инструмента → контекст агента» — S7

**Точка исполнения и область покрытия.** Реализовать в существующих адаптерах/брокерах проверку результата до его включения в следующий запрос модели, общую память либо публичный отчёт. Составить матрицу реально заявленных adapter/CLI versions: tool/result channel → точка перехвата → политика формата/размера/очистки → способ безопасной передачи → executed evidence → ограничения. Отдельно учитывать structured result, stdout/stderr, ошибки, streaming, вложения и ссылки на артефакты, повторное чтение и resume/cache. Наличие PostToolUse, пометки «untrusted» или regexp само по себе не квалифицирует профиль. Для каждого заявленного защищённого пути нужен тест реального порядка вызовов и захват следующего model request с синтетическими данными.

Если CLI не даёт перехватить данные до следующего model request, профиль получает `unsupported`/`unqualified` для этой возможности. Задачи, требующие защищённого приёма таких данных, блокируются либо направляются только в уже квалифицированный совместимый adapter с теми же полномочиями; неизвестный результат внешнего действия при этом не отправляется повторно. Ограничение должно быть видно до admission. Не объявлять все внешние CLI незащищёнными по результату чтения одного hook. Для автономного продолжения такого пути отсутствие доказанного перехвата — не pass; независимые задачи на других квалифицированных путях продолжаются.

**Правила обработки.** До передачи валидировать тип/схему, encoding, допустимые content types и лимиты bytes/records/depth; затем применять существующие согласованные правила удаления известных секретов и разделения данных/инструкций. Нормализованные исходы: allow, redacted, rejected, unavailable; это проектная семантика, точные wire enums версионируются при реализации. Результат указывает безопасный reason code и полноту содержимого. Чрезмерный, повреждённый или неподдерживаемый ответ не превращается в незаметно усечённый полный документ; если redaction уничтожила обязательные данные для критерия, остаётся missing evidence. Утверждённое извлечение части ответа допустимо лишь с явным статусом partial, provenance и проверкой пригодности, а не как способ обойти отказ.

В потоковом режиме ограниченно буферизовать полную проверяемую запись; не выпускать в модель фрагмент, который ещё нельзя проверить. Проверять секреты, разделённые между чанками, и суммарный лимит потока. Для multipart/артефактов проверять содержимое по заявленному безопасному decoder, а не только имя файла или URL; дальнейшее чтение проходит ту же границу. Не выполнять содержимое, не декодировать рекурсивно без лимита и не обещать универсального распознавания всех обфускаций. Ошибка/таймаут обработчика оставляет затронутый путь закрытым с безопасной диагностикой, без передачи сырого ответа.

**Секреты и полномочия.** Использовать синтетические canary-секреты без реальных credentials. Проверка должна показать их отсутствие в следующем запросе модели, резюме, общей памяти и публичном отчёте, в том числе в exception/stderr/cache пути. Сырой секретный ответ не записывать в обычные логи и evidence; при обоснованной необходимости сохранять только через уже авторизованное закрытое quarantine-хранилище, иначе не сохранять. Публичная диагностика не содержит секрет или его пригодный для перебора fingerprint. Сохраняются безопасные identifiers, версия политики и digest очищенного представления. Redaction не означает, что все возможные секреты всегда распознаются: гарантии ограничены заявленными форматами, каналами и проверенными профилями.

Текст документа/лога не меняет instruction hierarchy, tool grants, scope или требуемые approvals. Опасная команда внутри обычного примера кода не блокируется только из-за ключевых слов; попытка превратить данные в разрешение не создаёт authority независимо от решения классификатора. Предварительная проверка команды и полномочий остаётся обязательной: фильтр уже возвращённого ответа не отменяет выполненный опасный эффект. Prompt-injection containment проверять по реальным исходящим действиям, а не по одному ответу модели «я отказался».

**Стоимость и повторные отказы.** Измерять false positives на размеченных доброкачественных случаях, false negatives на отрицательных fixtures, latency/usage самой проверки и число повторных отказов по adapter/policy version. Denied/rejected outcome не запускает бесконечные переформулировки, платные judge-вызовы или fallback, обходящий то же правило; сохраняется circuit breaker F04 и unknown-outcome семантика F06. Порог допустимых ложных отказов и проверяемый набор закрепляются до квалификации; защита не считается успешной только потому, что отклоняет всё. Обязательный LLM-фильтр на каждый tool call не вводится.

### F26. Повторяемая проверка поведения перед обновлением агента — S7

**Триггер и выбор набора.** Расширить существующие M6/M7 проверки, change packages и парный подход F24; не устанавливать второй harness/evaluator. Каждая смена модели/профиля, промпта, сборщика или нормативного контекста, списка/версии/прав инструментов, обработки tool result либо схемы ответа оценивается на изменение поведения. Сохранять реальные изменённые paths/digests, общие и изменяемые факторы, affected capabilities, выбранный corpus и reason. Неопределённое влияние требует bounded impact analysis и, при неустранённой неопределённости, соответствующего обязательного набора или статуса blocked, но не автоматического skip. Доказанная опечатка вне исполняемых prompts/contracts не запускает платные модели. Этот selector не отменяет текущий source verifier, review, Trust CI и права на provider calls.

Регулярность означает повтор при каждом значимом изменении и явном обнаружении drift профиля, а не обязательный cron/job и не платный прогон при каждом чтении файла. F24 остаётся специальным набором для оптимизации контекста; его 12 сценариев переиспользуются, а не копируются в конкурентный корпус. Детерминированные contract/adapter tests запускаются без платного provider; живое сравнение проводится только для требующих его профилей с отдельным бюджетом и разрешением, отсутствие которых честно блокирует эту квалификацию.

**Корпус и независимая ожидаемая семантика.** Собирать versioned cases из существующих fixtures, прежних инцидентов и обычных/граничных задач. Case содержит устойчивый ID, provenance, замороженные входы и project snapshot, expected behavior, forbidden outcomes, criterion/rule IDs, исполняемый oracle/check, severity, required/optional и условия изоляции. Expected behavior — проверяемое свойство, не обязательное буквальное совпадение текста. Новый подтверждённый дефект получает регрессионный case по существующему bugfix-workflow. Секретные/клиентские данные заменяются разрешёнными synthetic fixtures; внешние holdout-наборы не копируются в недоверенный candidate.

Версии корпуса, oracle, thresholds и baseline выбирает доверенная сторона до candidate evaluation. Проверяемый агент не может записывать их, подменять ожидаемые ответы своими выходами или превращать собственный результат в новый baseline. Digest без сохранённого оригинала и независимого контроля записи недостаточен. Защиту от изменения baseline/вердиктов проверять на реальной файловой/сервисной границе, не только текстом инструкции. Изменение oracle/corpus создаёт новую версию и требует отдельного review; для нового сравнения оба варианта переоцениваются по одному принятому набору. Принятие нового baseline — отдельно зафиксированное решение уполномоченной стороны, не автоматическая реакция на fail кандидата.

**Парное выполнение и воспроизводимость.** Старый и новый варианты получают одинаковые закреплённые входы и общие условия: project snapshot, corpus, oracle, tool responses/fixtures, ресурсы, бюджеты и режим cache. Для намеренно изменяемых факторов сохраняются pins обоих вариантов; при смене контекста сами контексты могут отличаться, но все различия должны быть объявлены. Не смешивать результаты разных входов, toolchain или oracle под видом эффекта одной смены модели. Использовать изолированные сбрасываемые рабочие области, не общий mutable session state. Внешние write effects моделировать либо исполнять в отдельно разрешённой disposable среде; сравнение не должно дважды публиковать/платить в production.

Манифест сравнения связывает baseline/candidate identities, actual provider model/version (насколько раскрыта), prompts, tools, context и sanitizer profiles, corpus/oracle/config digests, run/case/attempt IDs и evidence. Для стохастики до запуска задать положительное число повторов N по случаю/профилю, budget ceiling, timeout, правила infra retry и допустимые отклонения; seeds/order фиксировать, когда поддерживаются. Все попытки, ошибки и недовыполненные повторы остаются в отчёте. Одиночный удачный запуск, cherry-pick, только длина ответа, число chunks или self-reported confidence не доказывают качество/стабильность.

**Вердикт и неизвестные значения.** Сначала оценивать предметные критерии, соблюдение полномочий/инвариантов, injection containment и ложные блокировки; затем rework, latency и полную стоимость F08/F09. Критическое нарушение либо неразрешённый эффект не компенсируется меньшими затратами. Остальные tolerances и число наблюдений объявляются до сравнения; без них стохастическая часть не квалифицирована. Длинный корректный ответ не хуже короткого только из-за размера; ответ прежней длины с неверной моделью насоса обязан провалить предметную проверку.

При отсутствующем исходном baseline фиксируется initial qualification, а не comparative pass; обязательная сравнительная квалификация остаётся незавершённой. Неисполненный required case, infra failure, неподтверждённый oracle или недостаточное число повторов не становятся pass. Применимые статусы различают pass/fail/blocked/inconclusive/not_applicable, причём not_applicable требует сохранённого основания, а skipped не считается passed. Неизвестные стоимость/confidence/token usage остаются unknown, старые исторические нули не переинтерпретируются как новое измерение. Если baseline-модель недоступна или её реальная идентичность изменилась, результат не выдаётся за точный парный эксперимент: сохраняются ограничения и требуется явно разрешённая новая baseline qualification, без ослабления safety gates.

**Человеческая приёмка и допуск.** При новом типе результата/предметном сценарии reviewer/владелец проверяет сами результаты по заранее выбранной выборке и все обязательные критические случаи/выявленные отклонения; выборка не состоит лишь из лучших примеров. Фиксировать проверяющего, criterion, result identity и вывод. LLM-as-judge может быть только отдельно проверенным вспомогательным инструментом, не обязательным новым проверяющим каждого вызова и не единственной властью принимать кандидата.

Перед применением нового поведения нужен полный принятый eval report на точных versions/inputs; сохранение такого отчёта — необходимое evidence, но не merge/deploy/production authority. Сначала реализовать и проверить механизм на детерминированных fake adapters; затем отдельно квалифицировать реальные поддерживаемые profiles. При провале оставить прежний квалифицированный профиль, если он остаётся безопасным; при обнаруженной уязвимости старого — остановить затронутую capability, а не откатываться в известный небезопасный режим. Ни successful benchmark, ни этот пакет не активируют M8 и не заменяют независимый Trust CI.

### 4.1. Минимальный контракт манифеста и связывания — F19–F24

| Поле / группа | Назначение |
|---|---|

| `target_repository`, `source_snapshot`, `change_id`, `route_id` | Однозначная идентичность задачи; source snapshot включает dirty-tree identity, если она применима. |

Метрики и время наблюдения записываются в существующий аудит F08–F11 и не меняют семантический digest. Обязательные тексты нельзя заменить сокращённой выдержкой без отдельно принятого изменения самих entrypoint-инструкций. Schema и bounds манифеста реализуются в U1: лимиты количества/размера записей, запрет секретных путей, проверка relative path/ref, tenant/repository isolation, rejection неизвестных полей. Локатор не разрешает произвольный network fetch или чтение `.env`. Таблица задаёт контракт проектирования, а не исполняемую конфигурацию текущей версии.

## 5. Общие инварианты

Любой положительный вывод связан с конкретными SHA, criterion и profile. Никакой agent-produced artifact не создаёт Trust CI authority. Нет live effects без действующего точного разрешения; security approvals подписывает человек вне agent environment. Нет новых GitHub Actions. Нет чтения `.env`/private keys агентом, поддельных tests/receipts/checks, изменения immutable release artifacts, скрытой повторной оплаты provider и потери существующих изменений.

Журнал не хранит скрытые reasoning streams. Квоты не обходятся дополнительными агентами. Rollback не удаляет исторические evidence и реальные побочные эффекты. Улучшение скорости не достигается снижением полноты функции, отключением проверок или исключением неудачных попыток из отчёта.

Внутри U3: U3a — F25, матрица перехвата и проверки AC59–AC67; U3b — F26, trigger/corpus/baseline/runner/report и AC68–AC77; U3c — уточнения F05/F22 и AC78–AC79; U3d — уточнения F06/F11/F17 и AC80–AC82. На каждый этап — отдельный небольшой PR/change package; этот umbrella не означает один гигантский code PR. Каждый этап: characterization/failing tests → узкая реализация → focused tests → полный применимый verifier → независимые route-selected reviews → свежие receipts → PR → внешний Trust CI на актуальных head/base. ## 9. Проверки и Definition of Done

Перед каждой реализацией на Claw: сначала обязательное измерение capacity по текущему `AGENTS.md`, затем entrypoint/state, отдельно `git status --short`, `git diff --stat` и обновление refs. Исторические числа CPU и agent slots не считаются текущей доступной ёмкостью. Существующие изменения сохранить; local route и grants не выдумывать. Проверить актуальные имена тестов/профиль, зависимости и disposable DB before execution.

Для изменённого product tree выполнить `python3 scripts/grok_verify.py --mode pr`, выбранные независимые review и финальную проверку дерева с сохранёнными reports. Factory PostgreSQL tests запускаются только в новой disposable PostgreSQL 17 DB; не читать production `.env` и не использовать Trust CI DSN. Mac build/tests выполняются в зарегистрированном профиле с сохранением exit status и `.xcresult`. Эти команды — требования будущей реализации, не результаты выполнения в этом пакете.

**Core accepted:** U1–U3 и Linux U6 приняты, включая F19–F26 и AC41–AC82 в заявленных поддерживаемых профилях; все применимые AC проходят; существующие проверки не ослаблены; реальные время/стоимость/предметная приёмка наблюдаемы. **Apple accepted:** дополнительно U4, Apple U6, AC38 и независимая проверка границы runner. **ML qualified:** только при выполненных U5 gates; может оставаться deferred без провала core. **Program complete:** core и обязательный Apple scope приняты либо его исключение явно записано владельцем; U7 оформлен; каждый deferred пункт видим.

Дополнительно к source gates: F25 требует end-to-end доказательства для каждого заявленного защищённого adapter path; F26 требует принятого корпуса/baseline, всех обязательных cases и отдельной предметной проверки нового результата. Поддержка stub/fake не выдаётся за покрытие реального CLI. Без разрешённого live запуска либо доступного baseline соответствующая qualification остаётся blocked/not_evaluated; не вся независимая работа останавливается. Новая source-проверка `--mode pr` выбирает допустимый профиль штатным selector и сохраняет причины skips; F26 не выдаёт дополнительных исключений.

Документ, открытый PR, successful local tests, accepted pilot и активированная M8 — разные статусы. Для принятия source PR нужен текущий App-owned `adaptive-trust-ci/verified@<policy-sha12>` на exact head и применимые человеческие подписи. Публикация и production требуют своих полномочий.

## 10. Включение и откат

Вводить изменения поэтапно: сначала измерение/объяснения, затем сравнение нового routing в observation mode, после regression gates — применение scope control. Обязательные safety gates не отключаются флагом эксперимента. Mac и SHAP default-off до своих qualification gates.

При регрессии F25/F26 остановить затронутое новое поведение, сохранить безопасные reports и наблюдать уже отправленные операции без повторной записи. Raw tool output не разрешается как fallback. Возврат только на прежний квалифицированный и не известный как уязвимый профиль; иначе capability остаётся закрытой. Новый baseline не принимается ради зелёной проверки.

При ошибке выбора контекста отключить оптимизированную навигацию, сохранить manifests/evidence и вернуться к прежнему авторитетному bootstrap; не использовать stale выдержки и не удалять журнал. При ошибке scope вернуть предыдущий рабочий профиль без удаления истории; остановить новые затронутые dispatch, сохранить и reconcile inflight jobs. При проблеме Mac запретить новые Apple jobs, завершить/отменить по lease и сохранить отчёты. При ошибке ML отключить прогнозы, не основной pipeline. Миграции только additive/forward recovery с проверкой старых readers: rollback кода не означает безопасный down-migration или удаление evidence.
