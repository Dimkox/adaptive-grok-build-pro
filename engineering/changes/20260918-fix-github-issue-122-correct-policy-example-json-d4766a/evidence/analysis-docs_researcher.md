# Documentation analysis — issue #122

## Findings

- `trust-ci/config/policy.example.json` presents three illustrative approval scopes: `governance` (including `trust-ci/**`, `.grok-stack/**`, `AGENTS.md`, `decisions.md`, `mistakes.md`, the Makefile and selected approval/review/verification scripts), `database` (SQL/migration paths), and `production` (infrastructure/deployment paths). Evidence: [`trust-ci/config/policy.example.json`](../../../../trust-ci/config/policy.example.json#L20-L55).
- That file is not a live policy source. Root README already describes repository-scoped profiles as a code/config capability awaiting separately reviewed and approved server-side policy/holdout installation, and says the capability does not change deployed policy or branch protection. Evidence: [`README.md`](../../../../README.md#L18-L21). Trust CI README explicitly calls the checked-in policy an illustrative example, distinguishes the placeholder digest, and says it does not establish that either repository is enabled. Evidence: [`trust-ci/README.md`](../../../../trust-ci/README.md#L13-L19).
- The rollout runbook copies the example into `runtime/policy.json` only as an initial setup step and immediately requires replacing placeholders; it does not assert that this copied file is already active. Evidence: [`engineering/runbooks/trust-ci-rollout.md`](../../../runbooks/trust-ci-rollout.md#L21-L47).
- The current-epoch operator procedure is already documented in Trust CI README: an administrator transfers the exact deployed policy through an authenticated human-owned channel; the operator keeps it outside the checkout and uses a private local copy. It explicitly says the API does not publish the policy document and that the repository example is not a substitute. The procedure computes Trust CI's normalized canonical policy digest and compares it with `/health/ready`'s `policy_digest`, stopping on mismatch. Evidence: [`trust-ci/README.md`](../../../../trust-ci/README.md#L256-L284). The document cautions against raw-file `sha256sum` and requires the human to check the exact repository/PR/base/head, missing scopes, Check Run owner, and epoch-named check before signing. Evidence: [`trust-ci/README.md`](../../../../trust-ci/README.md#L286-L290).
- The rollout runbook establishes the user-visible epoch evidence: the Check Run must use `adaptive-trust-ci/verified@<policy-sha12>` and be owned by the Trust CI GitHub App; it also requires rechecking on a fresh PR and after policy/holdout changes. Evidence: [`engineering/runbooks/trust-ci-rollout.md`](../../../runbooks/trust-ci-rollout.md#L52-L65). Trust CI README defines the suffix as a policy epoch and explains that a check from an older epoch is insufficient for the current protected-branch requirement. Evidence: [`trust-ci/README.md`](../../../../trust-ci/README.md#L5-L11).

## Safe documentation claims

1. Label `policy.example.json` as an illustrative starter/example. Its approval rules describe what that example would configure if deliberately installed as policy; they do not describe deployed approval requirements merely because the file is present in this repository or copied during bootstrap.
2. State that only the exact server-mounted policy and external holdout used by the deployed service govern live Trust CI behavior. Repository examples, local `runtime/policy.json`, local test output, and historical PR observations cannot prove today's deployed scopes or epoch.
3. Direct operators to the existing authenticated handoff plus `health/ready` comparison for the full normalized digest, and to the App-owned Check Run on the exact PR head for visible epoch evidence. A GitHub-visible check name reveals only the documented 12-hex policy-digest prefix; do not publish the full deployed policy or any credentials/private keys.
4. Say that the service API intentionally does not expose the policy document. The operator procedure obtains it separately from the service administrator using an authenticated human-owned channel and keeps its copy outside the checkout.
5. Do not claim that deployed policy omits the example's `governance` approval globs, or that a named historical PR proves current policy configuration, unless a current authenticated deployed-policy handoff and exact-head check establish those facts. Issue #122 reports historical green checks under epoch `06ecf1c875bc`, but this documentation task's checkout alone cannot independently establish the live server configuration.
