## Current contour

## Critical missing fact: merged commit

The present durable model proves a tested PR `head_sha`, not an exact merged commit. `webhooks.py` treats `closed` only as cancellation and discards GitHub's `merged`/`merge_commit_sha`; `trust_ci_jobs` and attestations have no merge record. The API also has no GitHub credential with which to query merge state. Consequently `POST /promotions` cannot honestly enforce “exact merged commit” by merely finding a passed job.

The design must choose and test one authoritative bridge before implementation:

1. Persist an HMAC-verified closed+merged webhook fact `(repository, pr_number, tested_head_sha, merge_commit_sha, merged_at)` and require the promotion commit to match it, while defining allowed merge methods; or
2. Add an independent exact-main-SHA validation job/attestation after merge and authorize only that commit.

Option 2 is the stronger invariant and avoids ambiguity from merge commits/squash commits that differ from the tested PR head. In either case, promotion acceptance must also require a stored `passed` attestation from the active policy epoch; signature validity alone is insufficient.

## Exact extension points

- **Contract/model:** add separate `PromotionPayloadV1` and `PromotionEnvelope` in `models.py`; do not overload the PR-shaped approval schema. Minimum signed fields: `schema_version`, `promotion_id`, `nonce`, `actor`, `key_id`, `repository`, exact merged `commit_sha`, exact `artifact_sha256`, constrained `target_environment`, `policy_digest`, `reason`, `issued_at`, `expires_at`. Keep canonical JSON and strict validators.
- **Signature:** add `sign_promotion`/`verify_promotion` in `signing.py`, using a dedicated trusted scope such as `production`. Verification must enforce repository allowlist, target environment allowlist, active policy digest, bounded TTL, current time, key lifecycle/scope and signature before any authorization record is returned.
- **Policy:** promotion environments/TTL must be policy-owned and included in `Policy.digest`; promotion signer scopes must not be derived from `approval_rules`, because those rules will become empty. Keep trust-store reload-on-request and readiness checks.
- **API:** add `POST /promotions` beside `/approvals`; reject kill-switch, malformed data, disallowed repo/environment, stale/future/expired envelopes, wrong epoch, absent/non-passed exact commit evidence, bad/revoked key and DB failure. Return 409 on ID/nonce replay. Never echo secrets or raw rejected payloads.
- **Store:** extend all three store surfaces with an atomic promotion insert plus accepted audit event, exact-tuple lookup/authorization, and safe rejection-audit support. Authorization reads must bind `(repository, commit_sha, artifact_sha256, target_environment, policy_digest)` and time validity; no “latest promotion” fallback.
- **Schema:** additive `004_promotions.sql` in both migration trees. Recommended immutable table: UUID promotion ID PK, globally unique nonce, repository, exact commit SHA, artifact SHA-256, constrained environment, policy digest, actor/key/reason, issued/expires, canonical payload JSONB, signature, created timestamp, and indexes for the exact authorization tuple and expiry. Add `promotion_id` to audit events or create a dedicated immutable promotion-event table; never update/delete accepted envelopes in routine flow.
- **Roles:** API gets only `SELECT, INSERT` on promotion records and `INSERT`/sequence access for their audit events. Worker needs only the minimum read if exact attestation linkage is checked by API SQL. Backup retains read-only access through migrator default privileges plus explicit grants as required by tests.
- **CLI/operations:** add offline `promotion-create`, `promotion-verify`, and `promotion-submit`, paralleling approval commands. Creation stays on the human-controlled workstation. A deployment consumer must verify the signed supply-chain bundle, compare its manifest `git_head` and chosen artifact digest byte-for-byte to the accepted promotion tuple, then fail closed before any production mutation.
- **Interactive-gate removal:** only after the deployed promotion contour is proven, deploy a policy with `approval_rules: []`. Do not remove the `/approvals` code/table in the same migration; retain compatibility/rollback first. Observe the new App-owned epoch check on a disposable PR, update branch protection to the new exact check name+App ID, and then retire `needs_approval` operational use.

## Rollout dependency

There are two distinct policy changes: repository code that adds the production authorization contour, and deployed server policy/branch protection that removes interactive PR approvals. Repository code alone cannot mutate deployed policy or protection. Rollout must therefore be: migrate/deploy compatible endpoint -> prove promotion acceptance and denial paths -> exercise a signed production envelope against the exact verified artifact -> deploy empty approval rules -> prove new epoch check -> atomically update branch protection. Rollback is previous images/policy plus the previous exact required check; additive promotion rows remain audit history.
