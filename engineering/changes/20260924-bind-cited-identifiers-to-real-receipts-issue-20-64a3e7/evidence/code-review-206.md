## Answers

**1. Can the echo lie? Yes — one branch, reproducibly.** `receipt_echo` re-reads from disk by *name* (`receipts.py:586-587`) instead of reporting the run that just happened. `verify()` skips `write_receipt` in three cases (`verification.py:1751`: `record and route and governance_check.status != 'fail' and source_stable`). Two are covered: no-route → the echo itself reports `reason=no-active-route` (`receipts.py:583-584`); unstable source → `report['tree_fingerprint']` is the *post*-run fingerprint so the guard at `receipts.py:598` fires. The **governance-fail branch is not**: the tree is untouched, so the stale receipt's fingerprint equals `expect_tree_fingerprint` and the guard passes. Reproduced in `/tmp/cite206-review/expA.py` (case A):

```
RECEIPT kind=verification status=pass fingerprint=aaaa…aaab at=2026-09-20T01:02:03+00:00 path=.grok-stack/runtime/receipts/r1/verification.json route=r1
```

That line came from a run that recorded nothing. Governance is configured here (`governance/rules`, `debt`, `canonical-examples`) and `_governance_check` returns `status='fail'` on any of `KeyError/RuntimeError/OSError/TypeError/ValueError` (`verification.py:276-289`), including time-dependent overdue-debt findings — so re-running `grok_verify --mode pr` unchanged and getting a governance fail is a live path in this repo. It is not *silent* in human mode (the adjacent `RESULT: FAIL` line and exit 1 remain), but the pasted artifact is indistinguishable. `stale` is worse: `invalidate_receipts` (`receipts.py:782-791`) stamps `stale: true` in place while keeping `status` and `tree_fingerprint`, and `receipt_echo` never reads that flag, nor the envelope checks `validate_evidence` performs (`receipts.py:733-748`). `--no-record` is correct (`grok_verify.py:44`). `grok_review.py` is safe: `write_receipt` raises before the echo on every refusal path, so its line is a faithful read-back. `--json` routing to stderr is correct and keeps stdout parseable.

**2. New laundering surface.** Prefix acceptance is *not* weak enough to matter by chance — measured: this repo's corpus is 436 files / 547 identifiers, 540 distinct 8-char prefixes, so a randomly fabricated 8-hex token hits at 0/20 000 samples (≈1.3e-7); 0/20 000 at 12 chars. The real surfaces are elsewhere: (a) `extended-citation` accepts the *incident shape itself* (see finding 3); (b) the corpus includes **agent-authored, git-tracked** documents (`citations.py:33-40`: `change-spec.yaml`, `state.json`, `route.json`) — a fabricated hex committed there is authoritative tree-wide, permanently, which is "becomes authoritative because it was written down once", the thing `corpus_identifiers` claims to refuse; (c) the CLI passes on documents it never read (finding 2). Keep the prefix rule; fix (a)-(c).

**3. All-numeric 40-hex git shas are never checked against git either. Only the decimal-only and >64 gaps matter; the `<3 distinct characters` rule is harmless.

## FINDINGS

1. **[major]** `.grok-stack/adaptive-grok/receipts.py:570-612` + `.grok-stack/adaptive_grok/verification.py:1751` — the echo reports a receipt by *name*, so a run that recorded nothing (governance fail) re-presents the previous run's `status=pass`, and an `invalidate_receipts`-stamped receipt echoes as `pass` too; reproduces as shown above. This violates the function's own docstring (`receipts.py:576`), `requirements.md` AC2 and README ("refuses to present an older receipt as a fresh one"), and is tool-generated false evidence — the exact class issue #206 is about. Fix: have `verify()`/`write_receipt` hand the just-written data (or a recorded-this-run flag) to the echo instead of re-reading by kind, and reject `data.get('stale') is True` plus the `validate_evidence` envelope fields (`receipt_id`/`kind`/`status`/`schema_version`) before rendering anything.

2. **[major]** `scripts/grok_citations.py:44-49,58-66` — a document that is never read (oversized > default 2 MiB, typo'd path, directory, FIFO) yields `UNREADABLE …` on stderr, `CITATION PASS: 0 token citation(s) … from 0 document(s)` and **exit 0**. Verified: `grok_citations.py big.md` → `exit=0`. An agent honestly reports a green check on an unchecked report, contradicting `requirements.md` ("named in the output rather than passing silently"). Fix: non-empty `unreadable` ⇒ `status='error'`, non-zero exit unless `--warn-only`; print the note on stdout; apply `--max-bytes` to stdin too.

3. **[minor]** `.grok-stack/adaptive_grok/citations.py:142-145` — `extended-citation` accepts a real identifier plus an invented tail whenever the real part stands alone in the corpus, which is 197 of 547 identifiers here (8- and 12-char route ids). Verified against this tree: citing `00652f60f78cdeadbeef` (real `00652f60f78c` + `deadbeef`) resolves. Zero test coverage (mutation in answer 7). Fix: delete the branch — a citation longer than every real identifier is never a faithful truncation — or allow it only when the token also resolves as a Git object.

4. **[minor]** `citations.py:33-40` — `engineering/changes/*/change-spec.yaml|state.json|route.json|human-gates.json` are hand-edited and git-tracked, so a fabricated hex committed into a package becomes permanent tree-wide machine state; the module docstring's "report prose is deliberately excluded" only excludes `.md`. Fix: restrict the corpus to files the stack itself writes (or require the token to sit under an identifier-bearing key such as `*fingerprint`/`*digest`/`tree_fingerprint`).

5. **[minor]** `citations.py:83-105` — symlinked *directories* under a corpus glob are followed, so `corpus_identifiers` can read outside the repository (verified) while `get_receipt` in the same trust domain is descriptor-safe per component (`receipts.py:615-640`). False against `requirements.md` "follows no symlinks"; with ~48 sibling worktrees here it also permits cross-worktree laundering. Fix: require `path.resolve().is_relative_to(root.resolve())`, or `os.lstat` each component; add a total-bytes bound.

6. **[minor]** `citations.py:27,56-64` — decimal-only and >64-char hex runs are never judged, yet README and AGENTS.md say the tool flags "any 8-64 hex token". Fix: report `ignored_runs=<n>` in the `CITATION` summary so an all-digit or sha512 fabrication is visible as declined, and word the docs as "8-64 hex containing at least one a-f".

7. **[minor]** `receipts.py:588-602` — echo diagnostics are malformed or misleading: `reason=` is unquoted and carries spaces and a colon (`reason=receipt cannot be read safely: Expecting value: line 1 column 7 (char 6) path=…`, reproduced), breaking the documented `key=value` grammar; `expected = None` at line 590 discards the already-known path so a corrupt receipt under a *live* route reports `path=…/<no-active-route>/verification.json`; `path=` is absolute in every unavailable line but relative in the success line, against README's `path=<rel>`; and the `tree-fingerprint-mismatch` line still carries a pasteable `fingerprint=`. Fix: slug or shell-quote `reason`, keep `expected`, normalise to repo-relative, and name the stale value `stale-fingerprint=` so it is not the paste target.

8. **[minor]** `receipts.py:604-612` — `data["kind"]`/`["status"]`/`["route_id"]` are unguarded `KeyError`s outside the earlier `try`: a receipt holding only `tree_fingerprint` (matching `expect_tree_fingerprint`) makes `grok_verify` traceback and exit non-zero *after* a recorded pass (`expB.py`, `KeyError: 'kind'` at `receipts.py:609`); a `verification.json` whose content says `kind=code_review` echoes `kind=code_review`, and one whose `route_id` is another route echoes `route=OTHER`, because `get_receipt` validates only the route_id charset. Fix: `if not data or not {'kind','status','tree_fingerprint','created_at','route_id'} <= data.keys() or data['route_id'] != route_id or data['kind'] != kind:` → the `unavailable` line.

9. **[note]** `citations.py:154,174` — `audit_documents` walks the corpus inside `find_unresolved` and then again for the summary; measured 2.1× (0.081 s single walk → 0.168 s audit). Fix: walk once and pass the set/counter down.

10. **[note]** `citations.py:115-131,158-165` — unbounded `git cat-file` spawns (7 ms each, ~37 s per 5 000 distinct unresolved tokens, no aggregate deadline) with an untested `GROK_CITATIONS_SKIP_GIT` hatch. Fix: one `git cat-file --batch-check` process, or cap probes and surface `git_probes_capped=true`.

11. **[note]** `citations.py:170-176` + `grok_citations.py:58-63` — `unresolved_count` is distinct tokens while `MISSING` lines are per-citation, so the summary can understate the lines above it; and documents are named by `path.name`, so two `report.md` inputs are indistinguishable in `cited at report.md:2`.

12. **[note]** `scripts/install_into.py:25-56`, `.grok-stack/config/managed.json` — `scripts/grok_citations.py` is not in the installed/managed set although this PR's skill and AGENTS.md text instruct every consumer to run it; add it to both lists in this change.

13. **[note]** `tests/test_citation_identifiers.py:114-123` and `engineering/changes/20260924-…/test-plan.md` — the oversized-corpus assertion in the test name is not exercised (`citations.py:101-102` unexecuted), no test covers `receipt-not-recorded` / the exception-reason / the stale-invalidation echo states, and the change package's test plan is still the empty scaffold, so the shared-memory requirement in `AGENTS.md` ("Do not keep the whole plan only in chat") is unmet on paper.
