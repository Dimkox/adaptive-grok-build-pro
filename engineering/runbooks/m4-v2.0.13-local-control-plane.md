# M4 / v2.0.13 local control-plane rollout and recovery

This runbook is an operator checklist for a separately authorized local rollout. It does not authorize a push, merge, tag, release, deployment, credential access, external write or production mutation. M4 remains an unaccepted source candidate until exact-tree local evidence and the separately required external Trust CI gates pass.

## Preconditions and hard no-go conditions

- Use PostgreSQL 17. The reconciler depends on PostgreSQL 17 `transaction_timeout` to bound the whole operation, in addition to decreasing statement timeouts.
- Provision a fresh operational database and bootstrap it directly through exact Factory schema `013`. This repair adds no migration because no M4 candidate has been accepted or authorized for persistent rollout and there is no supported deployed schema-`013` upgrade population.
- Keep any database created by an older unaccepted M4 candidate killed. Preserve or restore it only into a separately named comparison database; never point runtime at it and never upgrade it in place.
- Keep migrator-owner and runtime-login DSNs distinct. The runtime login must be a `NOINHERIT` member of `factory_runtime` and must not own Factory objects.
- Confirm a verified logical backup can be restored into the named comparison database before admitting durable intake.
- Stop on missing exact-tree verification/reviews, checksum drift, readiness failure, role escalation, unresolved unquarantined terminal accounting, or any capacity/audit inconsistency.

Leaving the next migration numbers unused also avoids collision with provisional M5 migrations `014` through `017`. A persistent-data repair discovered after intake requires a separately reviewed, dependency-coordinated forward migration; do not edit an applied migration, down-migrate or delete evidence.

## Killed start

1. Record the exact source commit, package digest, PostgreSQL 17 server version, database names, and schema migration checksums without recording credentials.
2. Enable the global kill before starting intake or claims.
3. Run `adaptive-factory-admin bootstrap-local` with the owner DSN and the separately provisioned runtime login. Require exact schema version `013` and immutable checksum agreement.
4. Start `adaptive-factory-server` only with the runtime DSN and its operator-owned absolute Unix socket. Require mode `0660`, a non-group/world-writable parent, and no TCP listener.
5. Confirm `/health/ready` reports the effective `factory_runtime` role, exact schema `013`, consistent live allocations/counters, persisted retry limits, and no unresolved terminal accounting without `accounting_blocked`.

## Admission smoke test

Keep global kill enabled except for the explicitly bounded synthetic claim window below, and keep every real repository killed throughout:

1. Verify authenticated health and fixed low-cardinality metrics without bodies, credentials, actor/repository/task identifiers, prompts or reasoning.
2. Prove the runtime role cannot mutate accepted intent, task events, audit, raw capacity, migration history or generic metrics.
3. Clear the synthetic repository kill, explicitly clear global kill only long enough to submit and claim one bounded synthetic task, then immediately re-enable global kill once the lease is acquired. A repository unkill never overrides global kill.
4. With global kill restored, reserve budget, observe and settle usage on the already leased synthetic task, advance/release the lease, and verify capacity/allocation plus fixed snapshot agreement.
5. Using the same bounded clear/re-enable sequence, claim a second synthetic lease and allow that lease to expire within its approved test timeout. Restart PostgreSQL, wait for the final PID 1 postmaster readiness condition, then reconcile the bounded page. The first pass repairs that expired work; a pass resumed from its returned cursor and a separate cursor-reset idempotency pass must each repair zero rows.
6. Verify the late pre-restart grant is stale-fenced, the audit chain is valid, and no reservation or capacity is silently lost.
7. Re-enable the repository kill, retain the synthetic evidence according to the approved local retention policy, and clear global kill only after every check is recorded as green.

## Recovery

On any fence, capacity, deadline, accounting, audit, authorization, isolation, timeout, restart or readiness failure:

1. Enable global kill, stop new intake/claims, and stop the Unix-socket process.
2. Preserve database rows, append-only audit, bounded logs and exact-tree evidence. Do not mutate the comparison copy or delete the failing operational database.
3. If failure occurred before first durable intake on an explicitly named disposable database, destroy only that exact disposable target and provision a fresh schema-`013` database.
4. If durable intake occurred, keep the database killed and diagnose against a separately restored comparison copy. Recover only through a separately reviewed, dependency-coordinated forward repair and its own disposable upgrade/restart evidence.
5. Repeat the killed-start and admission checks from the beginning. Calendar pressure never waives a failed gate.
