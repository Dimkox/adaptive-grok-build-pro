## Ownership and recovery

Landing SQLite retains WAL/FULL behavior and takes a nonblocking lifetime `landing.writer.lock` before opening or recovering state. The publication database independently takes `.intent-writer.lock`. Do not remove either lock to bypass a running writer. Do not share quarantine, scratch or artifact roots across different stores/operators. Server-owned resources close on composition failure, startup failure, ASGI shutdown and process exit; injected services remain caller-owned.

At most 100 interrupted landing rows are recovered per startup: accepted inputs become `input_unavailable_after_restart`; normalizing becomes `provider_outcome_ambiguous`; interrupted local render/evaluation becomes `local_run_interrupted`, all `needs_human`. Startup does not replay a model request. Larger interrupted populations require a separately controlled bounded recovery procedure. Artifact tampering fails closed. Ambiguous publication remains observation-only via its independent coordinator; no startup or restore automatically republishes.

`adaptive-landing-state backup --config <config> --snapshot <new-private-path>` requires the service and publication writer to be stopped: it acquires their same lifetime locks before snapshotting. It uses SQLite's backup API to include committed WAL-visible pages, creates standalone database files, copies the exact private artifact files and writes a manifest last. It refuses links, unexpected artifact names, overlapping roots and existing destinations. Limits are 4,096 files, 512 MiB per file, 4 GiB total I/O accounting and 180 seconds. Restore spends that same budget on hash verification and copying, so its payload must fit two passes (at most 2 GiB before other constraints). Known second-pass insufficiency returns `snapshot_budget` before any restore root is created; the cap and deadline are not reset. A saved snapshot is not a promise that it fits the restore budget. A failure leaves a partial directory for preservation; absence of the final manifest means no complete snapshot. It does not copy credentials, raw quarantine input, scratch, the source clone or the external deployment root.

The printed manifest SHA-256 must be retained separately with the snapshot record. It is integrity evidence, not production authority. Run backup/restore as the dedicated `adaptive-l5` data owner under their own exact operational authorization. Before restoration, stop the service/publication writer, set `live_enabled=false`, preserve the existing state/publication/artifact roots by moving them to explicitly named inactive locations, and leave the original configured paths absent. `adaptive-landing-state restore --config <config> --snapshot <path> --manifest-sha256 <saved-digest>` checks the closed manifest and file digests, refuses any existing destination and recreates only the exact original paths. This preserves absolute retained-artifact references without rewriting sealed records. Restore failure leaves partial new roots inactive; preserve them and do not start the service. The original deployment target is not reverted by this state restore; reconcile it by observation before any later publication action.

For a binary rollback, keep the service stopped, retain the current release/config/state snapshot and select the previous generated unit only when its landing schema and retained source epochs are compatible. Do not downgrade unknown schemas. A default-off restart of the current release with the same durable roots is the bounded containment path when compatibility is unknown. Activation/rollback of the site itself uses the exact persisted predecessor through the publication CLI, with its separate grant.
